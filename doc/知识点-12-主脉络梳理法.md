# 业务 agent 主脉络梳理法

> **缘起**：要读一个**基于 pi 核心包开发的业务 agent**（代码不在手边、且是 AI 堆砌出来的）。最初想从前端 2000 行的组件入手——**方向错了**：前端只是主脉络的末端，不是一条独立脉络。
>
> **一句话**：**主脉络是一条线，不是一棵树。**
>
> **本文件回答**「怎么把一条线拉出来」；pi 的接缝在哪，由 [开源项目导航手册/pi-接缝清单.md](开源项目导航手册/pi-接缝清单.md) 回答——那份是本文第 3 步的**内核侧半成品**。

---

## 〇、先钉死「主脉络」是什么（三个否定）

| 不是 | 为什么不行 |
|---|---|
| ❌ 不是**目录树** | 按层横切（前端 / 后端 / DB 各读一遍）会得到三份互不相干的清单，你依然不知道它们怎么连起来 |
| ❌ 不是**功能清单** | "有哪些页面 / 接口 / 字段"回答不了"它到底怎么跑起来" |
| ❌ 不是**前端一条、后端一条** | 那不是脉络，那是**切片**——切片之间没有因果，脉络有 |

✅ **主脉络 = 一次真实请求，从入口走到落地的完整纵向切面。**

**关键推论**：**前端是这条线的末端，不是另一条线。** 所以读前端的正确姿势是问"事件在哪接住、怎么变成 UI"，而不是"把这个组件的 2000 行读懂"——后者里有 80% 根本不在主脉络上。

---

## 一、五步法

### 第 0 步：选定「主干路径」——只选一条

**判据（三条都满足才选它）**：
1. 用户**最常走**的那条（不是最炫的，也不是最边缘的）
2. 它**穿过的层最多**（穿不过去的路径定不出脉络）
3. 它的**产出可验证**（你能说清"成了是什么样、败了是什么样"）

**产出（一句话）**：

> 用户做 ______ → 系统产出 ______

> ⚠️ 别一上来选"最复杂的流程"。复杂流程里绝大多数分支是**边缘情况**，它们挂在主干上，**不该在拉主干的时候读**。

---

### 第 1 步：找入口——主脉络的起点**应该只有一个**

```bash
# Next.js App Router：路由入口
grep -rn "export async function POST\|export async function GET" app/
find app -name "route.ts" -o -name "page.tsx"

# Server Actions / 内部调用
grep -rn '"use server"' app/
grep -rn 'fetch("/api/' app/ components/

# 顶层入口（如果是 CLI / 服务形态）
grep -rn "createAgentSession\|runAgentLoop\|AgentHarness" --include=*.ts .
```

**产出**：入口文件 `路径:行`。

> ⚠️⭐ **第一处关键判读**：如果你找到**好几个入口都能触发这条主流程**——**先停下，这是发现，不是麻烦**。AI 堆砌的代码最常见的病灶就是「同一件事被实现了多遍」（每加一个需求就复制一条链）。**"同一件事有几条实现"是你重构的第一个决定**，也是你读代码时最该记下来的一件事。先把它标进"脉络分叉"清单，再继续。

---

### 第 2 步：顺着**数据的路**往下走（只走数据，不走工具函数）

**唯一规则**：**只跟"数据从哪来、到哪去"，不跟工具函数。**

- 路标是 `import`：谁 import 谁 = 谁依赖谁
- 从一个函数进到下一个函数，只问"**它把什么交给了谁**"
- 遇到格式化、排序、校验、日期处理这类**纯计算**——**不进**，标一句"旁支"就跳过
- 遇到**内核接缝**（`runAgentLoop` / `AgentHarness` / `createAgentSession` / `AgentTool` / `systemPrompt` …）——**停一下，记一个挂点**，然后继续走过去

**产出：主脉络调用链**

| # | 层 / 环节 | 文件:行 | 它把什么交给了谁 | 内核接缝？（挂点号） |
|---|---|---|---|---|
| 1 | 入口 | | | — |
| 2 | | | | |
| 3 | | | | |

> ⚠️ **链条断了怎么办**：如果从 route 直接跳到数据库、中间没有任何一层——**别硬补**，如实记成"断点"。断点本身是 AI 堆砌的证据（因为人写的时候会自然分层），也是你后面要问人的问题之一。

---

### 第 3 步：在每个挂点上标「业务增量」——**这才是主脉络的真正内容**

一条线本身没有信息量（内核早就把顺序写死了）。**信息量全在挂点上**：业务在哪个接缝上加了什么。

对每个挂点问三句（借 `business-analysis` 的模块三问）：

1. **内核在这里做了什么**——⚠️ **去 pi 源码查，不许猜**（查法见 `pi-接缝清单.md`）
2. **业务在这里加了什么**
3. **业务为什么必须加**（不加会怎样）

**产出：挂点表**

| # | 内核接缝 | 内核侧是什么（file:line） | 业务侧实现（file:line） | 业务为什么加 | 证据强度 |
|---|---|---|---|---|---|
| 1 | `systemPrompt` | `harness/agent-harness.ts:526` | | | 🟢 查证 / 🟡 推断 / 🔴 待确认 |
| 2 | `AgentTool` | `agent/src/types.ts:406` | | | |
| 3 | `beforeToolCall` | `agent/src/types.ts:285` | | | |
| 4 | `convertToLlm` | `agent/src/types.ts:185` | | | |
| 5 | | | | | |

> ⭐ **这张表的左半边已经填好了**——就是 `pi-接缝清单.md` 里的接缝 → `file:line` → 搜索词三列。你只需要填右半边（业务侧）。**这是上一步交付物在这里的直接复用。**

---

### 第 4 步：把前端接回末端（**前端切面**，不是第二条脉络）

**核心判断（一句话判据）**：

> **一个前端文件 / 函数，如果它既不消费内核事件、也不产生用户意图 → 它不在主脉络上。**

主脉络在前端只承担**一段**：

```
内核事件流 ──subscribe──▶ 状态收拢（store / reducer） ──▶ 视图分支 ──▶ DOM
   ↑ 挂点：订阅点                      ↑ 挂点：状态形状              ↑ 旁支：样式/布局
用户意图（点击/提交） ──────────────────┘
   ↑ 挂点：动作入口
```

**产出：前端切面表**

| # | 环节 | 文件:行 | 说明 |
|---|---|---|---|
| 1 | 事件订阅点（`subscribe` / `useEffect`） | | 内核事件从哪进来 |
| 2 | 状态收拢（store / reducer / `useState` 群） | | 事件变成什么形状的状态 |
| 3 | 视图分支（条件渲染） | | 状态怎么决定看见什么 |
| 4 | 用户意图入口（handler） | | 用户动作怎么回到主脉络 |
| ✂️ | **旁支（不读）** | | 样式 / 布局 / 格式化 / 排序 / 数据变换 |

**那 2000 行组件怎么归位**：

| 那 2000 行里的东西 | 在主脉络上吗 | 怎么处理 |
|---|---|---|
| `subscribe` / 事件订阅 | ✅ 是（环节 1） | 精读 |
| 状态 → 视图的条件渲染 | ✅ 是（环节 2、3） | 精读，做成**决策表** |
| 提交 / 点击 handler | ✅ 是（环节 4） | 精读 |
| 数据变换（map / filter / 排序 / 格式化） | ❌ 旁支 | **整块跳过**，只记"这里做了 X" |
| 样式 / 布局 / 动画 | ❌ 旁支 | **整块跳过** |
| 分支里重复出现的同类判断 | ⚠️ **信号** | 进"概念缺失清单"，不进主脉络 |

> ⭐ **这一步是本次梳理的最大收益**：它把"要不要读那 2000 行"变成"**只需读其中约 1/5**"——而且读的是主脉络上的那一段。**你没有少读，你只是不再读旁支。**

---

### 第 5 步：验收——三个可检查信号

| # | 信号 | 通过标准 |
|---|---|---|
| 1 | **能说清"改哪儿"** | 给你一个新需求（如"加一个业务工具"），你能说出**要动哪几个文件、不需要动哪几个** |
| 2 | **能说清"字段的一生"** | 任取一个业务字段，你能说出它**存在哪、谁写它、谁读它** |
| 3 | **能对上真实日志** | 你画的时序图，能跟**一条真实 trace / 日志**逐环对上 |

三条全过 = 主脉络梳理完了。**过不了的那条，就是你还欠的那块。**

## 二、交付物：四张表（划出"不读"的范围才叫梳理）

| 表 | 作用 | 谁来填 |
|---|---|---|
| ① 主脉络调用链 | 骨架：一次请求经过谁 | 第 2 步 |
| ② 挂点表 | **内容**：每个接缝上业务加了什么 | 第 3 步（左半边有现成的） |
| ③ 前端切面表 | 主脉络的末端 | 第 4 步 |
| ④ **旁支清单（明确写"不读"）** | 范围：**这不是可选项** | 第 2、4 步随手记 |

> **为什么"不读清单"是必交项**：不划出范围，你永远会有"是不是还有没读到的"的焦虑，最后变成漫无目的地翻。**写下来，才算把这个范围关掉了。**

---

## 三、⚠️ AI 堆砌代码的三条特别警告

### 1. 主脉络可能不是一条线，而是 N 条重复实现
AI 每加一个功能倾向于复制一条链。所以第 2 步可能拉出**好几条**调用链。
**这不是你走错了，这是发现。** 把它记成「同一件事有 N 条实现」——这是重构的第一个决定，也是最值钱的结论之一。

### 2. 代码是**线索**，不是**证据**（修正一个前提）
`business-analysis` 说「以代码为准，代码比印象可靠」——**那条成立的前提是"代码是人写的"**。
AI 堆砌的代码里，**互相矛盾的分支会同时存在**（同一个状态既当 `loading` 又当 `error`；同一个字段两种格式）。
👉 所以挂点表里加了 **"证据强度"** 列：🟢 查证过 / 🟡 推断 / 🔴 待确认。**🔴 的必须回去问人，不许默认代码是对的。**

### 3. 别把"烂"当成"复杂"
2000 行 ≠ 2000 行的信息量。堆砌的代码是**摊开的**（不抽象 → 所有情况平铺），所以它反而**可以被机械抽提**。
先量一下：`useState` 几个、`if` 多少处。**如果 15 个 state + 80 处 if，它的真实信息量大概只有 200 行的表能装下——你要的是那张表。**

## 四、判据与停止条件

| 情况 | 动作 |
|---|---|
| 第 2 步拉出多条重复链 | ✅ 记下来，选**最完整的那条**当主干，其余记为"待收敛" |
| 30 分钟画不出挂点表 | ⚠️ 说明业务规则本身没被写清楚——**去问人**，别硬读代码 |
| 链条出现断点 | 如实记录，**别补** |
| 找不到任何内核接缝 | ⚠️ 可能你读的**不是这条主脉络**（或这个业务 agent 没真的用 pi 内核）——回到第 0 步重选 |
| 你不打算维护这套代码 | **只需要第 1 步 + 第 4 步**（知道在哪、前端读哪段），其余跳过 |

## 六、还没答案的地方（诚实的空白）

- **"入口应该只有一个"是我的判断，不是实测**。业务 agent 里多入口（HTTP + MQ + 定时任务）是合法的架构，那时"主干"要按业务语义选，而不是按入口数量判。**遇到这种，回来改这一条。**
- **挂点表能不能覆盖全部业务增量，未验证**。有可能业务的主力根本不在 pi 的接缝上，而在自己的编排层（那样主脉络的重心就要从"挂点"移到"编排"）。**这是本文最可能被推翻的一条。**
- 验证本方法的唯一方式是**真跑一遍**。截至写下这些字，**它还没有在任何一个真实业务 agent 上走完过**。
