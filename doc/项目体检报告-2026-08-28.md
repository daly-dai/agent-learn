## 1. 代码质量 — 8/10

**做得好的（有硬证据）：**

- **卫生指标近乎满分**：全项目非测试代码 0 处 `any`、0 处 TODO/FIXME，仅 3 处非空断言且都有前置守卫（`lib/permission/readonly.ts:144`、`lib/tools/bash/bash-runner.ts:120`）。外部评估（PLAN.md 7.5 的 E1-E6 清单）发现的问题已闭环处理，包括 E3 死代码清理、E4 `messageText` 重复实现收敛——E4 的处理方式体现了正确判断力：不是简单删一份，而是发现 manager 版有独立职责（compactionSummary 处理）后合并职责。
- **注释纪律是罕见的强项**：注释解释"为什么"而非"做什么"，带决策日期和上游参考。例如 `lib/types.ts:49-56` 解释了为什么 compactionSummary 要独立类型而不是伪装 user（伪装会让前端把它渲染成用户气泡）；`lib/session/store.ts:211-218` 完整记录了"孤儿 tool 导致 DeepSeek 400"这个真实 bug 的因果链和修法。这些注释本身就是学习材料。
- **函数粒度控制良好**：最大的 `deepseekModel.ts`（637 行）是内聚的适配器（两条转换边界 + 两条请求路径），不是失控的大文件；引擎、存储、权限模块都拆得干净。

**扣分点：**

- `app/lib/trace-fold.ts:93-138` 自称纯函数但内部直接 mutate rows（`foldOne`/`bumpStroke`/`closeSpan` 改传入对象）——现在没事，将来一加 memo 就会因为引用不稳定失效。
- 测试代码里有一批陈旧注释/命名（见第 2 节），和源码的高纪律形成反差。

## 2. 单元测试质量 — 7/10

**做得好的：**

- **纯函数层的测试接近生产级**。`lib/permission/readonly.test.ts`（22 用例）覆盖完整的 fail-closed 矩阵：走私语法（管道/重定向/命令替换）、只读命令带写参数（`find -exec`、`git tag v1.0` 创建、`npm audit fix`）、空命令。`app/api/chat/_pipeline/approval.test.ts:41-46` 里甚至有一条注释自我纠正宽松断言（"`not.toBe('block')` 会把误 allow 也放行"）——测试素养的自我进化痕迹。
- **隔离纪律严格**：全项目统一 `mkdtemp(tmpdir)` + 清理，环境变量保存还原（`bash-runner.test.ts:16-28`），零真实网络/真实模型依赖（用 `FakeModel implements TeachingModel`）。全项目没有一处 `vi.mock` 模块拦截，mock 全走依赖注入——"为可测性设计 seam"的正确示范。
- **测试名读得出行为和动机**，如 `manager.test.ts:44`"list() 只列合法会话：审批日志/副本不再冒充 0 条会话（幽灵会话回归）"。

**两处结构性硬伤：**

- **`lib/agent.ts`（引擎循环，347 行）零测试**。这是全项目"所有其他代码都在为它服务"的核心，但 block→伪造 isError 结果、rewrite 换参、工具抛错不崩循环、maxTurns 兜底、事件序列——这些最关键的行为全部未测。`FakeModel` 基建在 `summarize.test.ts` 里已经写好，复用成本很低。
- **`lib/deepseekModel.ts`（协议转换，637 行）零测试**。`toOpenAiMessages` 里的 toolResult/tool_call_id 配对（孤儿 tool 防线的第二道）、compactionSummary→user 伪装、SSE 坏 JSON 解析——全是纯函数或可用 stub fetch 驱动，可测性极好却未测。

- 条件断言可能静默跳过：`store.test.ts:111-119` 的 `if (firstKeptIndex > 0)` 包住断言，回归时测试照样绿。

## 4. 架构质量 — 8.5/10

项目最强的维度。**分层不是文档宣称，而是被 grep 验证的真实纪律**：

- provider 字段确实只在 `lib/deepseekModel.ts` 出现；引擎 `runAgentLoop` 只看统一协议。
- 前端全部 `fetch` 只在 `app/services/` 一处（`chat/index.ts:80`），组件/hooks 零绕过。
- E2 重构（route.ts 614→287 行 + `_pipeline/` 10 文件）质量过硬：审批决策抽成依赖注入的纯函数（`_pipeline/approval.ts`），编排层 `runPipeline` 只按序调用各阶段，SSE 管道细节留在 route 壳——边界划分的理由写在 `_pipeline/index.ts:12-17` 头注释里，连"未来 C13/C14 插在哪"都预埋了落点。
- 依赖倒置用得克制而准确：`TeachingModel` 接口、`ToolRegistry`、`beforeToolCall` 钩子（allow/block/rewrite 三态联合类型）——引擎对模型、工具、审批策略三者全部无感。

**扣分点（多数已被项目自己识别）：**

- 三个内存态 Map（`toolApprovals`/`userAnswers`/`runControllers`）单进程有效，多进程部署即失效（E6 已识别，条件触发）。
- 审批策略仍有硬编码残留（E5 归入 B5 hooks）。
- `approval-memory.ts` 用私有全局符号 `__sessionApprovals` 做状态，测试重置要靠硬编码符号名——应提供显式 reset 接口。

## 5. 可拓展性 — 7.5/10

- **加新工具** = 一个工厂文件 + 一行注册（`lib/tools/index.ts:68-85`），对扩展开放；**加新模型** = 实现 `TeachingModel` 接口；**加新管线阶段** = `_pipeline/index.ts` 按序插入。三条主要接缝全部通畅，且 `ARCHITECTURE.md` 第 3 节"七个接缝"把这个答案写成了文档——新会话的 AI 助手可以直接按图施工。
- **短板**：前端原语库刚起步（只有 Menu 一个）；hooks 注册表（B5）未做，beforeToolCall 是单钩子而非 onBeforeTool/onAfterTool 族；配置仍是 `.env.local` 散置（C7 只有骨架），距 pi 的"配置即文件"还有距离。PLAN 里都有排期，属于"已知且排队"而非"未意识到"。

## 前端专项 — 7.5/10

组件设计（page.tsx 只做"拿状态、派生数据、组装组件"三件事）、数据流（单向、无 prop drilling、无全局变量）、分层纪律（lib / services / components 边界被执行）、无障碍（alertdialog / aria 完整 / 焦点归还）都是强项。**三个真实缺陷值得优先处理：**

1. **SSE 流无 abort + 切会话帧污染竞态**（`use-agent-run.ts`）：run 进行中切会话，旧 run 的帧继续到达且 `applyFrame` 无 sessionId 校验，旧消息会追加进新会话视图，`done` 帧还会用旧会话的 stats 覆盖新会话。历史拉取有 AbortController（`use-sessions.ts:60-71`），同一个 hook 里两种请求取消策略不一致——修复模式照抄自己就行。
2. **TaskPanel dismissed 状态跨会话不同步**（`task-panel/index.tsx:41-46`）：`useState` 初始化只在挂载时读一次 localStorage，A 会话 dismiss 过，切到 B 会话且 B 的 todos 全完成时面板被错误隐藏。加 `key={sessionId}` 或 `useEffect([sessionId])` 即修。
3. **零 memo 化**：每个流式 delta 触发全树重渲染，正在流式的那条消息每个 delta 都让 react-markdown 全量 re-parse（`markdown.tsx` 注释自己也承认）——长会话快速流式下是真实卡顿风险。`foldEvents(observed)` 每次渲染全量重折叠（`page.tsx:188`）是累计 O(n²)。
