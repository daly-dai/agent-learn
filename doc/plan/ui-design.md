# doc/plan/ui-design —— 界面设计语言（走纸记录仪）

> 来源：PLAN.md 第十章（2026-08-26 PLAN 拆解时移入 doc/plan/）。**✅ 已实现**（`app/globals.css` 令牌 + 轨迹区折叠），视觉原则长期有效。

## 10.1 方向：走纸记录仪，不是聊天软件

这一页的工作只有一件：**让一次 run 变得可读**。所以视觉语言不取自 IM，而取自本文件自己用的那些词 —— 黑匣子、仪表盘、泳道、回放、seq。对应到实验室的走纸记录仪：

| 现实中的物件 | 页面上的角色 |
| --- | --- |
| 走纸（点阵纸） | 底色与轨迹区的纸纹，`background-attachment: local` 让纸随内容滚动 |
| 多支笔（每通道一色） | 一种事件通道 = 一种墨色，颜色只表示语义，不做装饰 |
| 记录条 | 轨迹区的时间脊线：轮次开带、输出成笔、工具成段 |
| 面板刻字 | 等宽字体承担全部标签与读数（它同时是本页的标题字） |

明度分三层，信息层级靠明度而非边框：**铭牌 `--plate`（最亮）> 走纸 `--paper`（阅读面）> 记录仪 `--recorder`（最暗）**。

## 10.2 令牌（`app/globals.css` 顶部即真相）

- 表面色：`--plate #ffffff`、`--paper #f8f8f8`、`--recorder #e4e4e4`、`--ink #1d2127`（**2026-08-26 三改**：暖调米灰 → 中性灰 → **纸感退役**走中性壳，见 §10.7；`--line/--line-soft` `#dcdcdc/#ececec`）
- 五支笔：`--pen-user #2f4b99`、`--pen-model #0b6857`、`--pen-tool #9c2b6e`、`--pen-signal #b0741b`、`--pen-error #a32d1f`（**保留**：功能语义色，不是纸的装饰）
- 字体：`Azeret Mono`（标签/读数/标题）+ `Instrument Sans`（正文，中文交给系统 PingFang SC / 微软雅黑）
- 两条硬约束：① 承载信息的文字对比度 ≥ 4.5:1（所以 `--ink-faint` 只用于装饰，amber 另留一个 `--pen-signal-ink` 文字版）；② 含中文的等宽标签不小于 11px、字距不超过 0.1em —— 汉字在同样字号下比拉丁字母更需要空间。

## 10.3 轨迹区做了三次聚合（`foldEvents`）

实测一次"列出工作区文件"的真实 run：**105 条 `message_update` + 12 条其它事件**。一行一条事件的画法会被 delta 淹没，所以前端按语义聚合，105 条塌成 2 行：

| 原始事件 | 记录行 | 为什么 |
| --- | --- | --- |
| `turn_start` | ◆ 轮次带 `T1` / `T2` | 轮次是真实序列，序号在这里是信息不是装饰 |
| 连续 `message_update` | ● 一笔墨迹，长度随字数 | 流式输出在物理上就是一支笔连续画一条线 |
| `tool_execution_start` + `end` | ■ 一段跨度，条长 = 真实耗时 | 工具执行有时长；配对靠 `toolCallId` |
| `tool_permission`（非 allow） | 信号行 | 放行是默认路径，只记真正的干预 |

配套的两个小决定：
- **前端自己给事件盖时间戳**（`ObservedEvent = { seq, at, event }`）。协议里 `AgentEvent` 没有 ts（Phase 0 才补），前端作为"观测者"盖到达时间，不改 `types.ts` 就能画出耗时与用时。等 `TraceEntry` 落地，这一层可以直接换成服务端的 `seq`/`ts`。
- **工具结果默认折叠**（超过 12 行），长文件不该淹掉对话。

## 10.4 仍然遵守"暂缓事项"

PLAN 九节写着"漂亮动画 / 复杂 UI"暂缓。这次只做了排版与信息结构，动效只保留三处、且都表示状态而非装饰：状态灯脉冲、流式笔尖、工具运行中的条。`prefers-reduced-motion` 下全部关闭。

## 10.5 V2 补记（2026-08-26）：尺度升级 + 溢出菜单

> 触发：用户 UI 反馈——"我不喜欢当前的 UI 风格，很小家子气，操作按钮很小，要是挤不下就不能放在 dropdown 里吗，所有面板也是。参考 reasonix、dsh、好多个开源项目。" 两个决策点用户已拍板：**34px 按钮 + 15px 正文**、**顶栏清空 + 会话行重命名/删除全进 ⋯ 菜单**。

**诊断（为什么"小家子气"）**：不是设计语言的问题（走纸记录仪 = 项目身份，保留），是**尺度与结构**的问题——全局 `.btn` 高约 28px、会话行操作按钮 2px 5px 内边距且 hover 才显示、绝大多数标签 10–11.5px、三栏各面板按钮样式互不通用、没有溢出通道（顶栏堆 model+run+状态灯+清空，会话行堆 ✎+×）。

**V2 四条决策**：

1. **尺度上提（令牌层）**：正文 14→15px、等宽标签 10–11→12px 起步；`--r` 3→6px、`--r-lg` 5→10px；新增 `--hit: 34px`（舒适命中区令牌，所有可点控件的最小高度）；侧栏 240→264px、轨迹 348→384px、对话列 830→880px、转录稿内边距 26→32px。风格未变（纸墨+五笔色），只是每样东西都大了一号。
2. **第一个原语：`Menu` 下拉菜单**（`app/components/ui/menu/`，B3 原语库的头一个）。DSH `dsh-client-ui-primitives` 思路：自研不引第三方。行为：点外/Esc/Tab 关闭、打开自动聚焦首项、↑↓ 循环/Home/End、危险项红色、禁用项跳过、aria（menu/menuitem/haspopup/expanded）。**它是独立交互岛**（阻止点击冒泡），可绝对定位到任意角落（会话行右上角）。
3. **溢出操作收纳**（用户原话"挤不下就放 dropdown"）：顶栏「⋯」收**清空记录**（危险操作不该高频露出）；会话行操作收进「⋯」菜单（重命名/删除·红，34px 命中区）。全站只保留这一个溢出模式。
   - **二次调整（2026-08-26，抄 DSH 会话列表）**：会话行 ⋯ 从"常驻显示"改回"**鼠标移上才显示**"（`opacity 0 + pointer-events none`，hover / focus-within 时显示）——行平时干净，干预才动手；34px 命中区保留（不是 V2 之前的 11px 悬停小按钮）。键盘可达性由 `:focus-within` 兜住。**触发按钮去边框（幽灵按钮）**：可点性靠 hover/聚焦的纸色底表达，不再靠描边（用户要求"不要边框，点击面积不变"）。**弹框侧开**（`align="side"`，用户要求"偏右，别挡会话列表"）：会话行 ⋯ 的弹框浮到侧栏右侧（转录稿上方），不再往下盖住下面会话行的标题/预览——absolute 定位会被 `.sessionList` 的 `overflow-y:auto` 裁剪，所以量取触发器视口坐标后以 `position:fixed` 定位；滚动/缩放时自动关闭（fixed 不跟随，浮错位置比关掉更糟）。
   - **三次调整（2026-08-26，用户拍板删除清空会话）**：清空记录是 Phase 1 单会话时代遗产——多会话下被「新建/删除」覆盖，且它**连确认弹框都没有**（静默抹历史，比删除还危险）。功能删除后**顶栏 ⋯ 菜单整个移除**（页头只剩信息：run/模型/状态灯，零操作按钮）。服务端 `DELETE /api/chat` + `services.clearHistory` 保留，供未来斜杠命令（/clear 等）复用。
   - **会话标题规则（不展示文件 id）**：标题行 = `title ?? preview ?? "未命名会话"`——session 文件 id（`s_2026-08-26T..._xxx`）是存储细节，不是给人看的名字，任何地方不显示；重命名草稿只回填已有标题（没标题从空输入开始）。
4. **高频操作放大**：发送/停止 40px、新建会话实心主按钮 34px、审批卡片按钮 42px、确认/提问卡按钮 36px、状态灯镜头 11→14px、轨迹读数盘 15→18px。

**验收口径**：① 全站可点控件命中区 ≥34px（图标按钮 34×34、主按钮更高）② 等宽标签最小 12px ③ 会话行/顶栏零个"hover 才出现的小按钮" ④ `tsc --noEmit` 通过。剩余待办：菜单只接入了顶栏和会话行，后续新操作（导出/设置/斜杠命令）都往 ⋯ 里加；B3 的 dialog/collapse/select 等原语按同一模式继续长。
   - **口径落地（2026-08-28）**：② 等宽标签 12px 全站收口——19 处 <12px（approvalKey 10.5、compactionTag/callTag 10、rowTime/sessionMeta 11 等）全部提到 12px（10 个 CSS 文件，含 markdown th / code-copy / alarmTag）。核查依据：这 19 处全部是信息承载元素（时间戳/键帽/徽章/提示/表头），无纯装饰豁免；若后续观感觉得某处 12px 突兀，改的是口径（如"辅助提示 ≥11px 豁免"）不是硬提字号。

## 10.6 V2 补记（2026-08-26）：AI 开发页面的约束纪律

> 触发：用户问"他们（参考项目）是怎么约束 AI 对页面的开发的，总不能想一出是一出"。查证：deepseek-harness 仓库根目录有 AGENTS.md，`packages/client/` 还有一份专门的 "Web client stack" AGENTS.md——**约束 AI 写前端在参考项目里是显式工程实践**（本会话的系统提示词就是 DSH 约束 AI 的活标本：工具规则/不许自建 dev server/提交前展示）。把结论写成显式规则，进本详案。

**五层约束（参考项目通用做法，我们项目已全部具备）**：

| 层 | 机制 | 我们项目的对应 |
|---|---|---|
| ① 令牌 | CSS 变量自动生效，AI 没有理由自创颜色/圆角/字号 | `globals.css :root`（`--plate`/`--pen-*`/`--hit`） |
| ② 组件 | 组合 > 发明，新原语必须走评审 | `app/components/ui/menu/`（B3 原语库） |
| ③ 文档 | 身份 + 硬约束（对比度 ≥4.5:1、等宽 ≥12px、命中区 ≥34px） | 本文件 |
| ④ 代码即约束 | 违反 = 编译错误，不是口头提醒 | `tsc --noEmit` 每步可运行、CSS Modules、类型系统 |
| ⑤ 流程 | 人审兜底：提交前展示清单、确认后执行 | AGENTS.md 第 9 条、PLAN 7.3 排期（范围约束） |

**硬规则（组件组合 > 发明）**：UI 改动默认只允许动令牌 / 既有组件 / 既有样式；需要新视觉元素或新原语时，必须说明"为什么现有原语库不够"，并对照 Radix/DSH 行为清单，经确认后再做。

**B3 精读任务（已排进 PLAN B3 行）**：精读 DSH [`packages/client/AGENTS.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/AGENTS.md)（"Web client stack"）——参考项目怎么约束 AI 写前端的直接教材。

## 10.7 V2 补记（2026-08-26）：纸感退役，走"中性壳"

> 触发：用户连续两问——"我不喜欢这个背景颜色"（暖调米灰）→ "侧边是灰色 中间是白色 好看吗？**为啥一定要纸感？？**"。第二个问题戳破了前提：**走纸记录仪是之前会话继承的设计决定，不是用户需求**。用户从未拍板过这个身份。拍板：纸感退役。

**退役了什么**：
1. 暖调米色底（V2 第二次调整已改中性灰）——本轮之前已完成
2. **点阵纸背景**（轨迹区 `radial-gradient`）——本轮删除，轨迹区变纯色面板
3. "纸/墨/笔"词汇只留在代码注释里当历史（视觉不再表达纸）

**留下了什么（为什么留）**：
1. **五支笔色**（user/model/tool/signal/error）——它们是**功能语义色**（消息角色 / 事件通道），不是纸的装饰。删了颜色就分不清谁在说话
2. **等宽标签与读数**——工具感，不是纸感
3. **明度三层**（plate > paper > recorder）——信息层级靠明度而非边框，这条结构原则与纸无关

**新的表面色**（Linear/Notion/DSH 同构的中性壳）：

| 令牌 | 值 | 角色 |
|---|---|---|
| `--plate` | `#ffffff` | 顶栏 / 浮层 / 卡片 |
| `--paper` | `#f8f8f8` | 阅读面（视觉即白色） |
| `--recorder` | `#e4e4e4` | 侧栏 / 轨迹（明确灰，与阅读面拉开落差） |
| `--line` | `#dcdcdc` | 边框 |
| `--line-soft` | `#ececec` | 细分隔线 |

**构图**：中间白（阅读面）+ 两侧灰（会话栏 / 轨迹）——"灰色侧边栏 + 白色中间"成立的关键是**落差够**（白 vs #e4e4e4 ≈ 20 单位），之前 #e0e0e0/#ececec 只差 12 单位，糊在一起才不好看。

**教训（写给自己）**：设计身份是用户的需求，不是 AI 的发明。AI 给一个主题时，要标注"这是继承决定，不是你的需求"——用户有权利随时丢弃它。§10.1 的走纸记录仪描述保留为历史，不再作为当前方向。

## 10.8 V2 补记（2026-08-28）：原语库评估——dialog/mask 出局，删除确认就地化

> 触发：用户问"哪些原语组件值得封装"→ 逐组件精读后**推翻了两个候选原语**。核心教训：**"值得封装"的判据不是"看起来像什么"，而是"重复度 + 未来复用者数量"**。

**原语候选评估（基于代码事实，不是拍脑袋）**：

| 候选原语 | 评估 | 结论 |
|---|---|---|
| `ui/dialog/` 模态骨架 | 唯一使用者 confirm-dialog（删除会话），而删除确认改行内后使用者归零 | ❌ 不封装 |
| `ui/mask/` 遮罩层 | 全站只有 confirm-dialog 一个 mask，approval/ask-user 都是底部卡片（无遮罩）——"重复度最高"是误判 | ❌ 不封装（并入 dialog 也不需要了） |
| `useGlobalKeydown` hook | 只有 approval-dialog 一个全局监听者，menu/ask-user 都是局部 onKeyDown | ❌ 不封装（一个 adapter = 假设的 seam） |
| `ui/select` / `collapse` / `stepper` | collapse 只有 TaskPanel 一个使用者；select/stepper 无真实需求点 | ❌ 不封装（按需原则） |
| **`app/lib/keys.ts` 纯函数层** | **真实重复**：approval 有内联实现（埋在 useEffect 不可测）、menu 缺 isPlainKey 防护（Ctrl+方向键也触发导航的隐患） | ✅ 封装 |

**删除确认改造（B3-③ 联动）**：confirm-dialog（居中 mask 弹框）退役删除（-155 行），改为**行内确认条**——复用 session-list 已有的"行内重命名"模式（状态替换行内容）：点 ⋯→删除 后该行原地变成"删除后不可恢复 [取消][删除]"红字确认条。**全站从此零模态弹框**（审批/提问本就钉底部，删除就地确认），mask 彻底出局。

**keys.ts seam 设计**（教学点）：收**最小结构**（`{ctrlKey,metaKey,altKey}` / `{tagName?}`）而非真实 DOM 事件 → node 环境直接单测（B8 ① 许可），无需 jsdom。接入：approval-dialog 内联判定搬出、menu 补 isPlainKey 防护。
