## 0. 这一课要回答的问题

**skill = 一个目录 + `SKILL.md`**。模型遇到匹配任务时，**按需**把它的正文加载进上下文。

核心矛盾（一句话）：

> 几十个技能的**正文**全塞进上下文会爆；只放**清单**、正文按需取，是唯一可行的规模方案。
> 这个"清单常驻 + 正文按需"就是 progressive disclosure，也是 C8 的全部。

**技能的三层**（官方标准，`agentskills.io/client-implementation/adding-skills-support`）：

| 层 | 内容 | 何时进上下文 | 代价 |
|---|---|---|---|
| 1 目录 | `name` + `description` | 会话开始就常驻 | 每技能约 50–100 token |
| 2 正文 | `SKILL.md` 全文 | 被激活时 | 建议 < 5000 token |
| 3 资源 | `scripts/` `references/` `assets/` | 正文引用到它们时 | 不定 |

## 1. 依据（一手证据链，都可复查）

### 1.1 标准怎么说

> **How does the model access skill content?** If the model has file-reading capabilities, it can read `SKILL.md` files directly. **Otherwise**, you'll provide a dedicated tool or inject skill content into the prompt programmatically.

→ **专用工具是标准里给"宿主没有文件读取能力"留的那条路。** 我们和 pi 都有文件读取能力，所以选工具路线是**主动加固**，不是照抄标准。

### 1.2 pi（主参考）：走"读文件"路线

|---|---|

| 形态改成 `SKILL.md` 是为了对齐 Codex CLI | `3b2b9abff` |
| 清单进 **system prompt**，每条带**绝对路径** `<location>` | `packages/coding-agent/src/core/skills.ts:355` `formatSkillsForPrompt` |
| 措辞是**条件版**："when the task matches its description" | 同上 `:365` |

| 它**自己承认**模型常常不读 | `b29de1c73` / `c12d18483` / `a4cb9ff02`（2026-01-25，三个 docs commit，**不是 fix**） |

→ **pi 的设计目标不是"加载最可靠"，而是"复用宿主已有的文件读取能力、不新增工具"。**

### 1.3 DSH（我在运行的 harness）：走"专用工具"路线

| 事实 | 位置 |
|---|---|
| 工具名 `skill`，参数只有 `name` | `packages/skill/tool-skill/src/index.ts:81-86` |
| 描述是**时序版**："…**before acting on** a task that names or clearly matches that skill" | 同上 `:83` |
| 返回**结构化**：`{ name, provider, resourceBase(directory\|url\|opaque), content }` | 同上 `:87-124` |
| 清单**只有名字 + 描述**（无路径） | 同上 `:319-321` `- \`name\`: description` |
| 清单是**持久 user 消息**，按条目 digest 差异**追加替换** | 同上 `:254-335` |
| 两条加载路径（工具 / 用户 `/skill:name`）**共用一个渲染**，并明写防双载 | 同上 `:267`、README |
| 可见性策略：`modelInvocable × userInvocable` 四组合 | `packages/skill/skill/src/index.ts:51,127` |

### 1.4 两家思路的分水岭（一句话）

> **pi：加载 skill 是"模型的通用能力"** —— 系统只负责**告知**（有什么、在哪）。
> **DSH：加载 skill 是"harness 的一等动作"** —— 系统负责**引导 + 治理**（何时调、返回什么结构、谁能看见）。

由此推出一条可复用判据（本项目可用）：

> **要"保证"的东西 → 写进 schema / 工具描述；"提示一下"就够的东西 → 写进提示词。**

## 3. 逐题

> 每题格式：**在问什么** → **机制（为什么不显然）** → **选项** → **➡️ 推荐** → **决定（待填）**

### Q1 清单放哪里：system prompt，还是做成一条会话消息？

**在问什么**：那 29 条 `名字 + 描述`，放在 **① 每请求现拼的 system prompt**，还是 **② 写进会话历史的一条真消息**。

**机制**：每次请求发给模型的东西是两段拼起来的 ——`① system prompt`（一段文字）+ `② messages[]`（会话历史，落盘在 `.sessions/*.jsonl`）。**清单只能待在这两处之一。** 而两处性质完全不同：

| | ① system prompt（pi 形状） | ② 会话消息（DSH 形状） |
|---|---|---|
| 何时生成 | **每请求现拼** | 某一刻写进历史，**之后一直躺着** |
| 技能集合变了 | 下个请求自动最新 | 历史里那条**过期** → 必须再追加一条"新清单，替换之前所有" |
| 落盘 / 轨迹 / 压缩 / token 统计 | 都不进 | **全进** |
| 模型看到几份 | 永远一份 | 换过一次就**两份**，靠提示词让它只看新的 |

⭐ **DSH 的"digest 差异替换"是被"清单是历史消息"这个前提逼出来的**：选了 ② 就必须解决"历史里那张旧清单怎么办"。它选 ② 的原因是自己的会话是"**日志 + 投影**"架构（凡是模型看到的都要能从日志重放，且有多 agent 作用域），system prompt 不是日志的一部分。

**我们的处境**（实测）：`route.ts:156` = `systemPrompt: buildSystemPrompt()`，**每请求现拼、不进历史**。

- 选 ①：零新机制，清单永远最新、永远一份。代价 = system prompt 一变，DeepSeek 前缀缓存失效 —— **这个代价我们已经在付**（"当前时间"每天都在变），而技能集合几乎不变。
- 选 ②：要新做三件事（**发布 / 差异比较 / 替换**），换来的好处是"system prompt 稳定"。**那三件事解决的是我们没有的问题。**

类比：① = 门口贴**今日值班表**，每天重打一张；② = 往**档案夹**里塞值班表，换班了再塞一张写着"以此为准"的。我们门口那块牌子本来就每天重打（要写今天几号），多贴一张不花额外功夫。

**选项**：① system prompt 每请求现拼　② 会话消息 + 差异替换　③ 每轮重新注入

**➡️ 推荐 ①。**

**决定（2026-09-15，用户定）**：**① —— 不写进会话文件。** 清单每次请求现拼，落在 `messages[0]` 的 system 那段里，不进 `.sessions/*.jsonl`。
**注意**：这只决定**名单**放哪；**正文**的加载动作两边一样（调 `skill` 工具 → 正文变成一条 `role:"tool"` 消息 → 落盘 → 之后每轮重发）。

### Q2 扫哪些技能根？

**在问什么**：模型能看到哪些目录下的技能。

**机制**：标准推荐两档 —— **项目级**（`<项目>/.agents/skills`，跨客户端约定）+ **用户级**（`~/.agents/skills`）。DSH 做了**六层 rank 优先级**（项目 > 用户 > 内置…）。

**实测事实**：`~/.agents/skills` = 29 个；`~/.claude/skills` = 25 个（其中 **5+ 与前者同名**）；项目内 `.agents/skills` **还不存在**。

**选项**：
- A 只 `~/.agents/skills`
- B A + 项目 `.agents/skills`
- C B + `~/.claude/skills`（兼容 Claude Code）

**➡️ 推荐 B。** `.agents/skills` 是标准明写的跨客户端约定，**项目级技能（"这个仓库专属流程"）正是最常用的场景**，建了才有。**C 不选**：那 25 个里有 5+ 同名，加它就得先造一套同名优先级 —— **为"兼容"付机制税，换来的主要是你已有的重复副本**（`available()` 的老规矩：一个 adapter = 假设的 seam）。DSH 的六层 rank 同样不抄，只做"项目 > 用户"两级。

**决定（2026-09-15，用户定）**：**A —— 只扫用户级 `~/.agents/skills`。** 项目级 `.agents/skills` 与 `~/.claude/skills` 本版都不扫：这一版先把"技能能被加载"跑通，**项目定制化留到完善阶段**。
（上面那条"推荐 B"是本次讨论中途的推荐，**未采纳** —— 采纳的是更小的一版。）
**连带收益**：只有一个根 ⇒ 第二层的「同名怎么裁决 + 来源怎么标注」从"跨根优先级"降级为"同一根内重名"这个边界情况，**"来源标注"整项取消**。

### Q3 遇到坏技能怎么办？

**在问什么**：`SKILL.md` 的 frontmatter 写坏了 / 缺 `description` / 名字不合法时，整体失败还是跳过。

**机制**：技能文件是**外部数据**（你手写、随时可能写错）。两个参照都选了"**宽容 + 诊断**"：codex 的 `SkillRootLoader` 每个根的错误单独收集；pi 生成 warnings 但尽量加载；DSH 有 `SkillDiagnostic` 概念。

**选项**：
- A 一个坏文件 → 整体加载失败（fail-loud，直接抛）
- B 跳过坏的、其余照常，**但诊断必须可见**（列表 / 日志里看得到）
- C 跳过坏的，静默

**➡️ 推荐 B。判据是「数据是谁写的」**：注册表（`lib/commands`）是**我们**写的 → 重名直接 throw，家规不变；技能文件是**你**写的 → 一个 YAML 缩进错不该让整个 agent 起不来。
**C 禁止**：静默失败 = 幽灵会话那个 bug 的翻版（"列得出"和"删得掉"必须是同一把尺；同理"加载失败"必须看得见）。

**决定（2026-09-15，用户定）**：**B —— 跳过坏的、其余照常，诊断必须看得见**；并加一条身份规则：**技能的身份 = 目录名**（同一目录下目录名天然唯一 ⇒ 同名冲突问题从结构上消失）；frontmatter 的 `name` 降级为**校验项**，与目录名不符 → 出一条可见诊断、**仍按目录名加载**。
**不做 kebab-case 正则校验**（不抄 opencode 的 `^[a-z0-9]+(-[a-z0-9]+)*$`）：本项目技能是中文场景，非 kebab 的名字是正常的，正则只会制造假失败。
**实测事实（本轮查的）**：29 个技能**全部**有 frontmatter、有 name、有 description，且 **name 全等于目录名** —— 今天一个坏技能都没有，这条规则是为将来兜底。

### Q4 用户入口一期做到哪？

**在问什么**：`/skills`（列技能）、`/skill:<name>`（用户强制加载）、`/model`（C13 遗留）三个命令，一期做几个。

**机制**：C13 的命令注册表 `lib/commands/types.ts:13` **早就预留了 `source: "builtin" | "skill"`**，就等着这一步。另外 pi/Claude Code 都有 `/skill:name` —— 它存在的理由是**模型不读时的确定性兜底**。

**选项**：
- A 只 `/skills`（列表）
- B `/skills` + `/skill:<name>`（强制加载）
- C B + `/model`

**➡️ 推荐 B；`/model` 放 C8 收尾的最后一批。** 理由：`disable-model-invocation` 这个开关**没有 `/skill:<name>` 就是死开关**（技能只能模型调，模型不调就永远进不来）→ B 属 C8 主链路。`/model` 只依赖 config + `selectModel`，零依赖、纯前端，放最后做**不会卡主线**，同时仍兑现 2026-09-01 那次的拍板。

**决定（2026-09-15，用户定）**：**B —— 做 `/skills` + `/skill:<name>`**（细节见下），**`/model` 本版不做**。
**面板形态（用户口述的验收形态，出自 C13 的斜杠面板）**：输入 `/` 弹出面板 → **上半是命令、一条分割线、下面是技能列表** → **模糊匹配** → 选中技能后，**技能名以高亮形式留在输入框里**。
**`/model` 移出 C8 的理由（用户 2026-09-15）**：暂不着急；且**模型适配层现在是手写的**，后续打算**改用 OpenAI 相关的 npm 包**来降低开发成本 —— 适配层可能整体重写，届时再定 `/model` 更省事。
⚠️ **面板属于页面/UI 改动 → 动手前必须先 `skill(frontend-design)`**（AGENTS 第 11.8 条，硬规则不设例外）；组件拆分与 hook 抽取按第 11.9 条（500 行触发线 / hook 管状态与副作用、纯函数管数据变换）。

### Q5 资源层（`scripts/` `references/`）一期做不做？

**在问什么**：技能正文里引用了 `references/xxx.md` 或 `scripts/run.sh`，模型怎么拿到它们。

**机制**：真技能是带脚本的（`docx` / `xlsx` / `tdd` 都是）。但**我们的 `read_file` 被 `resolveInsideWorkspace` 关在工作区内**，而技能根在工作区外 → **模型读不到**。

**选项**：
- A 只加载正文，**但在返回里说明资源目录在哪、要用就用 `bash` 读/跑（会弹审批）**
- B 给 `read_file` 加一条"技能根只读白名单"
- C 不说明（模型以为正文就是全部）

**➡️ 推荐 A。** A 让模型**知道**资源在哪（信息不缺），同时**不动家规**："agent 只能在工作区里动文件"是一条**结构保证**，为技能开第二个根属于**性质变更**，该由真摩擦逼出来（不变量 3：接缝由需求逼出来）。**C 是静默失败，禁止。** **B 记为升级路径** —— 真机发现"每个资源都要点一次批准"很烦时再上。

**决定（2026-09-15，用户定）**：**A**，具体形状：
1. `skill` 工具返回 **正文 + 技能目录绝对路径 + 文件清单**（照 opencode 限最多 10 个相对名）+ 一句"**相对路径相对这个目录解析**"；

### Q6 加载动作要不要审批？

**在问什么**：`skill` 工具进不进 `TOOLS_NEEDING_CONFIRM`。

**机制**：我们现在的机制是"**不在那个列表里 = 自动放行**"，`read_file` / `grep` / `find` / `web_fetch` / `web_search` 都走这条。

**必须一起认下的信任边界**：技能正文是**从外部拿到的指令**，它会**不经人批准地影响模型行为**（pi 文档的 Security 警告说的就是这个）。我们的兜底不变：正文若要模型**动手**，`bash` / 写文件**仍然弹框**。

**选项**：A 只读自动放行（照 `read_file`/`web_fetch` 先例，并在工具文件头写明）　B 每次加载弹框

**➡️ 推荐 A。** 选 B 会让技能体系每次加载都打断你 —— **真正要防的是"动手"，不是"读"**。

**决定（2026-09-15，用户定）**：**A —— 自动放行**（不进 `TOOLS_NEEDING_CONFIRM`，照 `read_file` / `web_fetch` 先例，并在工具文件头写明）。信任边界照上面那条认下。
**"自带脚本会不会危险"（用户本轮提出的疑虑）—— 查证结论**：
1. **本机脚本今天干净**：10 个 py 脚本的 import 只有 `argparse/csv/json/sys/os/zipfile/posixpath/re/datetime/copy` + `docx/lxml/openpyxl`；**无网络、无 `subprocess`、无 `eval/exec`、无删目录**（`subprocess`/`shutil` 只出现在 `tests/`）。
2. **自动放行不会让脚本自动跑**：`skill` 只读一个文本文件；脚本要跑必须再调 `bash`，而 `py xxx.py` 不在只读表里（`lib/permission/readonly/index.ts:57-59` 只认 `python --version`）⇒ **必弹框**。
3. **"自带"≠ 可信**：技能来自公共仓库，pull 一个新技能脚本就可能不干净 ⇒ **别把"脚本今天干净"当安全边界，边界是 bash 那一次弹框。**
4. ⚠️ **查出一个免审批的外发口子**（本版不决定，已记为下一轮题目）：`read_file` + `web_fetch` 双自动放行 ⇒ 坏技能可指挥模型"读工作区文件 → 发到外部地址"。**缓解事实**：`.env.local`（含 API key）在工作区**外**，`read_file` 读不到 ⇒ 可外发内容被限制在 `workspace/` 内。

### Q7 压缩要不要保护技能正文？

**在问什么**：技能正文作为 toolResult 进上下文后，触发压缩时会不会被摘要吃掉。

**机制（实测）**：`lib/summarize/index.ts:26` 的 `TOOL_RESULT_MAX_CHARS = 2000` —— 压缩时**进摘要请求的 toolResult 视图只有 2000 字符**，而你的技能正文多在 3,000–10,700 字符；压缩之后原始 toolResult 又已不在折叠视图里。标准专门有一节 *"Protect skill content from context compaction"*。

**但触发概率极低**：我们的压缩阈值 ≈ 984K（窗口 1M − 预留），真机**从没遇到过**。

**选项**：
- A 什么都不做，**只把决定记进本文件**
- B 给技能来源的 toolResult 打标记，压缩时豁免
- C 压缩后自动重新注入已加载技能

**➡️ 推荐 A。** 依据是数据：没有真机样本，而 B/C 都要动刚重构完的压缩层（C18）。记进本文件 + 留触发条件（真机遇到"压缩后技能失效"再开）。**这不叫偷懒，这是你自己立的规矩**：没数据不动手。

**决定（2026-09-15，用户定）**：**A —— 什么都不做，只把决定记进本文件。** 触发条件（真机遇到"压缩后技能失效"再开）：技能正文作为 `toolResult` 进上下文后，压缩摘要只看到它前 2,000 字符（`lib/summarize/index.ts:26`），压缩后原始结果又不在折叠视图里。

### Q8 工具名 + 描述措辞

**在问什么**：工具叫 `skill` 还是 `skill_load`；描述抄 pi 的**条件版**还是 DSH 的**时序版**。

**机制**：名字是模型唯一的入口线索；描述措辞直接决定它会不会在正确的时机调用。
- pi：*"Use the read tool to load a skill's file **when the task matches its description**"*（软条件，它自己承认模型常常不照做）
- DSH：*"Call this with the exact skill name … **before acting on** a task that names or clearly matches that skill"*（硬时序）

**➡️ 推荐：名字 `skill`；措辞用**时序版**。** 名字与 `/skill:<name>` **同词**（人和模型说的是同一个词，少一层翻译）。措辞选时序版是**我们选 DSH 路线的唯一实质收益** —— 不这么选，我们就只是多花一个工具、拿回 pi 的老问题。

**决定（2026-09-15，用户定）**：**名字 = `skill`**（和 `/skill:<name>` 同词）。**描述措辞留到下一轮** —— 它必须包含 Q5 定下的两条红线，现在写等于猜。
**公平记下被放弃的那条**：`load_skill` 也不是没道理（本项目有一半工具是「动词_名词」：`read_file` / `write_file` / `edit_file` / `delete_file` / `list_files` / `write_note`），但 `bash` / `grep` / `find` 这些是裸名词，风格本就不统一；**决定性理由是与 `/skill:` 同词**。

## 7. 补记 1（2026-09-15 同日）：手势加载路径的源码级证据

> **触发原因**：用户问「我指定了 `/frontend-design`，你是如何装载的？需要 AI 再执行一个 `skill` 工具吗，还是直接把内容传给大模型？」——这是一个**本稿此前只能凭观察猜**的问题（第二层列着「`/skill:<name>` 的注入形态（user 消息 vs toolResult）　← 已解锁」但没证据）。
> **做法**：精读本机 DSH 的三个包（`dsh-tool-skill` / `dsh-skill` / `dsh-api-session-controller`），成文 `doc/知识点-10-DSH-skill装载机制.md`（含全部 `文件:行号` 坐标 + 自检题）。

### 7.1 定论：手势路径**零工具调用**

DSH 的 `/名字` 由**宿主在 `agent/pre-step` 钩子里直接注入**（`dsh-tool-skill/lib/index.js:168-202`），模型收到的正文是**一条 `user` 角色的指令上下文消息**，**不是 toolResult**，模型侧没有任何工具调用。工具路径（模型自己调 `skill`）是另一条独立入口。

→ **这直接回答了第二层那条「注入形态」**：**user 消息**。且两条路径**共用 `renderSkillContent`**（`dsh-skill/lib/index.js:57-70`），形态逐字一致。

### 7.2 本稿此前没有的 4 条机械事实（施工单要用）

| # | 事实 | 对我们意味着什么 |
|---|---|---|
| 1 | 注入**追加在该步所有注入的最后**（`index.js:200`）——"背景在前，待办材料在最后" | 我们排布"背景注入 vs 本轮任务"时可直接沿用这个位置语义 |
| 2 | 手势只扫 `source.kind === "user"` 的消息（`index.js:384`）⇒ **注入无法自我触发** | 可复用判据：**"文本能触发 + 会往上下文塞东西"的机制，触发源必须白名单化** |
| 3 | 注入消息带来源标记 `source: { kind: "skill-invocation", name, form: "instructions" }` | ⭐ 直接服务 **A3 轨迹视图**：能区分"用户真打的字"与"宿主注入的块" |
| 4 | 目录按 `sha256(name, description)` 差异比较（`index.js:301-304`），空目录用于作废旧名字 | ✅ **反向印证 Q1**：这套机制是"清单=历史消息"逼出来的，我们选了 system prompt ⇒ 确实无需这套 |

### 7.3 ⚠️ 一条与 Q3 冲突、必须改过来的地方

**DSH 对未知名字、以及 `userInvocable: false` 的名字，一律"静默当普通行文"**（上游 README 原话：*"未知名称与用户不可调用的名称保持为普通行文"*）。→ 用户把 `/frontend-desgin` 打错，**没有任何反馈**。

这与我们 **Q3 定下的原则直接冲突**（"跳过坏的、但**诊断必须可见**"；判据是"静默失败 = 幽灵会话那个 bug 的翻版"）。

**→ 我们的决定不是抄它，而是反过来**：`/skill:<name>` 指向一个不存在的技能（或该技能不可用户调用）时，**必须给一条可见诊断**（不静默）。

### 7.4 ⚠️ 一条会让中文技能名静默失效的坑（比上一条更硬）

DSH 的手势正则是**严格 kebab-case + 空白边界**（`index.js:373`）：

```js
/(^|\s)\/([a-z0-9]+(?:-[a-z0-9]+)*)(?=\s|$)/g
```

**我们 Q3 已经明确不抄 kebab 校验**（理由：本项目是中文场景，非 kebab 的名字是正常的）。两条合起来 ⇒ **我们的手势正则不能照抄这一个**：照抄了，名字叫「前端设计」的技能**永远触发不了手势，而且是静默的**（正好撞上 7.3 那个坑）。

→ **施工要求**：手势的**名字匹配规则**必须与**技能身份规则**（Q3：身份 = 目录名）**用同一把尺**，不能一个宽松一个严格。

### 7.5 顺带浮出的两个新差异（不拍板，记为下一轮的题）

1. **`/skill:<name>`（带冒号） vs DSH 的 `/名字`（裸斜杠）** —— Q4 定的是带冒号的那种。**两者取舍**：带冒号**不误伤**正常斜杠文本（`/usr/bin`、`5/8`、路径），裸斜杠**少打字且与技能名同词**。DSH 选裸斜杠的代价，就是必须写一个**排他正则**去躲路径与分数（`index.js:373` 的注释专门解释了这一点）。→ **下一轮定**。
2. **注入点落在我们代码的哪里？** DSH 每 step 都有机会注入（`agent/pre-step`）。**"我们有没有这个接缝"需要实读 `lib/agent/index.ts` 确认**——若没有，注入只能落在**请求装配处**（一次性），语义上比 DSH 弱一层（它每步都能重新判定）。⚠️ 红线提示：若要动 `lib/agent/index.ts`，**必须先走 pi 对照 + 用户确认**（AGENTS 第 0 条）。**本补记不下结论。**

**→ 两条都已解（2026-09-15 第三/四轮）**：① 拼写选了**裸名** `/名字`（R3-1），躲路径/分数的办法不是写排他正则，而是**拿 token 去技能名单里查**（查不中就不注入）；② 实读确认 **我们没有 pre-step 接缝**（`RunAgentLoopOptions` 只有 `beforeToolCall` + `onEvent`），注入落在**请求装配处**（`_pipeline/index.ts`）。**因此本功能不需要动 `lib/agent/index.ts`（红线文件）** —— 这正好也避开了 AGENTS 第 0 条的额外流程。

### 9.2 T1 施工中定下的 4 件小事（详案没写到，但必须留档）

1. **文件清单 = 递归收集、相对路径、排除 SKILL.md**。为什么递归：资源长在 `scripts/` 里，只列出一个 `scripts/` 对模型没用，它得知道**跑哪个**脚本。为什么排除 SKILL.md：正文已经给模型了。真实数据里 `code-review` 带 `agents/openai.yaml` —— **一层列表会漏掉它**。
