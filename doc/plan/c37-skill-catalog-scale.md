# C37 · 技能清单的规模策略：可见技能上百时，提示词里那份清单怎么办

## 一、需求（要做什么）

用户原话（2026-09-17）：**「客户安装上百个 skill 都可能，系统提示词可能会过多」**。

**现状（实测，非推断）**：清单**每请求现拼进系统提示词**（C8 的 §5 第 1 条，判据写的是「**模型看到的 = 全部技能 − 隐藏的**」）。

| 实测（本机） | 值 |
|---|---|
| 可见条数 | **21 条** |
| 清单总字符 | **4,390** |
| 每条均值 | **209 字符** |
| 最长一条 | `code-review` **434 字符** |

**线性外推（⚠️ 都是外推，没有上百条的真机数据）**：50 条 ≈ 10,450 · **100 条 ≈ 20,900（≈7,000 tokens）** · 200 条 ≈ 41,800 字符。

## 二、参考（各家怎么做，一手）

⚠️ **没有一家真正解决它**：

| 家 | 做法 | 代价 / 差别 |
|---|---|---|
| **Reasonix** | 封**整块**（`IndexMaxChars = 4000`，`skill/index.go:12`） | 超出的技能**整条不进清单** = **静默失效** |
| **pi** | **完全不封**（`core/skills.ts:355-383`：每条 name + description + `<location>`，5 行 XML） | **比我们还啰嗦**；它那两个常量（`MAX_NAME_LENGTH=64` / `MAX_DESCRIPTION_LENGTH=1024`）是**规范校验**、不是体积控制（超了只报 warning、description 原样保留） |
| **DSH** | 封**每条**（`descriptionMaxLength = 500`，`tool-skill/src/index.ts:27,391-393`） | **总量不封**；而且 **500 对我们等于没生效**（最长才 434） |

⭐ **DSH 另有一条架构差别**：它的清单**不进系统提示词**，是一条 `source.kind === "skill-catalog"` 的 **user 消息**、带 digest（**技能集合变了才重新发布**）。

⚠️ **家数口径对不上（2026-09-18 发现，待更）**：本节只有 **3 家**的一手材料（Reasonix / pi / DSH），而池子行的依据格原写「**五家**一手对照」、本文件第六节引的池子行原文写着「**四家**都没答案」—— **三个数字互不相同**。开工前二选一：① 把 codex / opencode 的一手补齐（若它们确实没有规模控制，就写明「**查过，没有**」）② 把口径统一成实际查过的家数。

## 三、候选方向（未拍板）

| | 方向 | 已知的代价 |
|---|---|---|
| **甲** | 截每条 description（DSH 式） | 我们的描述本来就不长，**压不住总量** |
| **乙** | 封总数 + **如实报数** | 照 Reasonix 但补上它缺的那句「还有 N 个未列出」 |
| **丙** | 改成**能查**（提示词只留"有 N 个技能 + 一个查找入口"） | 要有一个查找入口 |
| **丁** | 换落点（照 DSH 挪出系统提示词、进带标记的 user 消息 + digest） | 架构级改动 |
| **戊** | 封总数，把超出上限的那部分**降级成「只有 name」** | 见下（用户 2026-09-17 追加，**"需要"已被确认**） |

**用户 2026-09-17 追加定性原话**：「**name 上限这个确实是需要的，不然 skill 多了确实太多了**」⇒ **不再是"我觉得更好"**。

**⚠️ 戊 的边界必须记清**：它**不是** Reasonix 的「整条踢掉」（那会让技能**静默失效**），**也不是** pi 的「全量渲染」；它保留「这个技能存在、可以用 `skill` 加载」这个最低限度的信息，只砍掉**每请求都付**的描述成本。与乙叠加时，仍须按 **C22** 的母原则**如实报数**。

**⚠️ 戊 的代价（同日一起记，免得只记好处）**：`description` 是模型判断「**这活该不该用这个技能**」的**唯一依据**（`lib/skill/index.ts` 的 `Skill.description` 注释原话）—— 砍成裸名字 ⇒ 模型要么**乱加载**（白花一次工具调用去试）、要么**当它不存在**（等于技能没装）。
⇒ 所以 戊 **大概率要与 丙（改成能查）配套**才成立：**只留名字 = 必须给模型一个"按名字查描述"的入口**，否则砍掉的不是成本、是功能。
