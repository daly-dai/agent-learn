## 八、复查报告（2026-09-21 开工）

> 形态按 5.0 定的：每条**结论 + 证据**（`file:line` / 真机样本 / `.traces/` 引用）。

### ① 契约与语义 —— ✅ **一致，判"不改"**（理由可检验）

三处并排（这就是证据）：

| 处境 | 怎么处理 | 模型看到什么 |
|---|---|---|
| HTTP 非 2xx（403/404/429） | **算结果**（`ok:true` + `status`） | `Fetched <url> (HTTP 403)` + **错误页正文**（`fetcher/index.ts:143-152`） |
| 搜索无结果 | **算结果**（明说） | 「这次搜索没有返回任何来源。换个说法再搜，或如实告诉用户你没查到。」（`web-search/index.ts:269-273`） |
| 内容类型不支持（PDF / 图片） | **抛错** | `web_fetch 不支持这个内容类型：…`（`web-fetch/index.ts:90-96`） |
| 协议坏掉 / 被闸门拦 / 超时 / 字符集解不了 / 重定向超限 | **抛错**（`isError`） | 失败原因标签 + `detail` |

⇒ **边界是清楚的**：**"外部世界给的东西"永远是结果**（哪怕它是个错误页——"需要登录""慢一点"本身就是最有用的信息）；**抛错只给"我们要的东西拿不到 / 拿回来不能用"**。另一条不变量两侧都成立：**绝不给模型空字符串**（搜索那句明说、fetch 有状态码 + 正文）。

### ② 限额与截断（含 **C22**）—— ⚠️ **确认缺陷，判"修一半"**

**现状：三层上限被压成一个布尔。**

| 层 | 在哪 | 上限 |
|---|---|---|
| 抓取（字节） | `fetcher/index.ts:253-302` `readCapped` | `maxBytes` = 1 MiB（到顶 `reader.cancel()`，**剩下的字节永远拿不到**） |
| 转换（字符） | `convertHtml`（HTML→Markdown） | 自己的字符上限 |
| 呈现（字符） | `render/index.ts:78-104` | `maxOutputChars` = 200k |

三者在 `web-fetch/index.ts:108` 被 `||` 成一个 `bodyTruncated` ⇒ `details.truncated` **只有一个布尔**；模型看到的 footer 只有一句「内容已截断。要读全文，请抓一个更具体的 URL…」——**它不知道是哪一层截的、也不知道被截掉了多少**。搜索结果侧**同病**：`mergeSearchResults` 把"我们按上限砍的（`dropped`）"与"子查询自己带回来的 truncated" `||` 成一个布尔（`web-search/index.ts:247-248`）。

**判定**（按定稿写死的标准"截断必须能区分上游截的与我们截的"）：**做不到**。但 **⑧ 的一手对照把这个判定改了两处** ⇒ 最终处置：**② 本身不改代码，产出一个新池子项**。

#### ② 的修正（一手对照推翻了我自己的两个判词）

| 我原来判 | 一手证据（2026-09-21 读源码） | 改成 |
|---|---|---|
| 分层标志**要修** | ⭐ **DSH 的截断出口也只给一个布尔**：`web-fetch-http/src/provider.ts` 内部确实有 `truncatedByBytes` 与 `truncatedByChars` **两个变量**（注释还强调"只数真正丢掉的字节"），但**出口 `truncated: truncatedByBytes \|\| truncatedByChars`（:175）**；到工具层 `tool-web/src/fetch.ts:332` 又 `\|\|` 一次 ⇒ **成熟参考的模型可见出口也不分层** | **不做**（我们与 DSH 出口同级；且现有 footer 文案「要读全文，请抓一个更具体的 URL」对两层**都成立**）。触发条件：出现"模型需要知道是哪一层截的"的真实案例 |
| 「留一份 + 给路径」**不做**（记档） | ⭐ **两家都做了**：opencode `ToolRegistry.Materialization.settle` = "generic model-output bounding boundary and owns **managed retention paths**"（`packages/core/src/tool/AGENTS.md` §Output），模型拿到 `outputPaths`；**DSH 有一套通用 spill 栈**（`dsh-spill-local` + `dsh-spill-policy`）——showcase 测试原话："**formatted fetch result is automatically retained and spilled with NO tool-specific spill code**"，模型可见文本只多一句 spill 通知 ⇒ 这不是"锦上添花"，是**能力差距**：我们的截断是**永久丢弃**（`reader.cancel()`），模型再也拿不到那部分 | **升格为独立项**（新池子行 **C44**）—— 它要的是**新的一层**（落盘 + 保留/清理策略 + 把定位给模型 + 与围栏的关系），不是复查里顺手能修的 |

### ③ 内容与编码 —— 计划结论：**已知边界，不改**（把代价写清 + 触发条件）

- 现状：`parseCharset` **只看响应头**、不嗅探 `<meta charset>`（`fetcher/index.ts:216-223`），与 DSH 一致（A5 详案 7.6.4 #11）；按声明编码解码，**认不出的 charset 抛错而不猜**（宁可报错也不返回乱码）。
- 代价（如实写）：**只在 `<meta>` 里声明 charset 的页面会被按 UTF-8 解码 ⇒ 乱码**。A5 真机那次修的是"响应头声明了 GBK"的页面。
- ⚠️ **要真机证据才算复查**：需要一个"只在 meta 里声明 GBK"的真实 URL。**没有样本就不把这条写成"无害"** —— 先标 ⏳ 待样本；若长期拿不到 ⇒ 按"已知边界"记档并写明触发条件。

### ④ 安全 —— ✅ **结论：不改（依据齐，且我方比 opencode 严）**

| 块 | 现状（证据） | 判定 |
|---|---|---|
| 地址闸门 | `ssrf/`：11 种 `BlockedReason`（scheme / credentials / loopback / private / link-local / cgnat / unspecified / multicast / reserved / unparseable / resolve-failed）+ **逐跳重新过闸门** | ✅ 够；**对照**：opencode 的 webfetch **只校验 scheme**（`core/src/tool/webfetch.ts:85-87`），防护靠"**人批准**（permission 弹框）" ⇒ 我们这条比它严 |
| 重定向 | 见 5.3（保留我方 + 逐跳过闸门） | ✅ 已拍板；**对照**：DSH 更严（跨源直接拒 `WEB_REDIRECT_BLOCKED`），opencode 不设 `redirect` ⇒ 默认 follow |
| DNS rebinding TOCTOU | 刻意不做 IP 钉连接，残余风险明写在 `ssrf/index.ts:14-21`（上次 A5 正是死在自定义 lookup 上） | ✅ 记档不改（诚实边界） |
| 注入防御 | `EXTERNAL_CONTENT_NOTICE` 是**标注不是隔离**（`render/index.ts:22-25`）；对照 DSH `tool-web/src/trust.ts` 全文 7 行、也是标注 | ✅ 记档不改；**真机证据**：`i73jtz` 那次注入测试，模型明确拒绝执行并解释"外部内容只能当资料" |
