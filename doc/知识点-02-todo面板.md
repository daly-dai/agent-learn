# todo 面板：任务清单是怎么"活"起来的

> 本文回答三个问题：
> 1. 任务清单（todo）存在哪？怎么设计？
> 2. 状态（待办/进行中/完成）是怎么更新的？
> 3. todo 的状态更新和"模型调用工具"这件事是什么关系？

---

## 一、核心思想：todo 是"会话事件"，不是独立存储

先问一个问题：模型说"我要做三件事"，这三件事**存在哪**？

有两个选择：

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 独立存储 | 专门建一个 todos.json，单独读写 | 和对话脱节：回放会话时看不到"当时任务是什么"；删会话时还要记得删它 |
| B. 会话事件 | todo 就是会话里的一条记录，和消息一起写进同一个文件 | 和对话同生命周期：可回放、可审计、删会话一起删 |

我们选了 **B**（参考 DSH 的结论：todo 是会话事件不是独立存储）。

落地：我们的会话文件是 JSONL（一行一条记录），todo 就是其中一种记录类型：

```
{ "type": "message",  ... }   ← 一条消息
{ "type": "message",  ... }   ← 一条消息
{ "type": "todo",  "todos": [ {content:"写排序", status:"in_progress"}, ... ] }   ← 一条任务清单
{ "type": "message",  ... }   ← 后面的消息
```

**todo 和消息平级、混在同一个文件里、按时间先后排列**——这就是"会话事件"的含义：它是对话这条时间线上的一笔记录，不是旁边另开的小本本。

---

## 二、数据模型：三个状态

一条任务长这样：

```ts
type TodoItem = {
  content: string;                              // 任务内容："写一个排序算法"
  status: "pending" | "in_progress" | "completed";  // 待办 | 进行中 | 完成
};
```

三态就像"待办清单上的勾选进度"：
- **pending**：还没开始
- **in_progress**：正在做（**最多只有一个**——模型一次只专心做一件事）
- **completed**：做完了

---

## 三、方法核心：整表替换（幂等）

模型怎么告诉系统"任务清单变成这样了"？通过一个叫 `todo_write` 的工具。

**关键设计：整表替换**——模型每次调用都发**完整的清单**，系统直接拿新清单替换旧清单：

```ts
// 模型调用 todo_write({ todos: [...] })
// 系统：把你发来的整张表存下来，不管之前的表是什么
await store.appendTodo(args.todos);
```

**为什么不用"只更新变化的那条"？** 因为大模型不可靠——你让它"把第 2 条改成完成"，它可能改错位置、漏改、发明一条新的。**让它每次都重发整张表，就永远不会"漂移"**：反正以最新整表为准，旧的直接覆盖。

这叫**幂等**：同一张表发两次，结果一样。就像"把桌面的文件全删了重新拷贝一份"——不管之前什么状态，最后一定是这份。

配套一个校验函数 `validateTodos`，防止模型发来垃圾数据：
- content 去空格后不能为空（"任务内容不能是空白"）
- 去重（同一条任务不能出现两次）
- 最多一个 in_progress（"正在做"只能有一个）

---

## 四、状态是怎么更新的：一条完整的链路

现在把整条链路走一遍——**从模型的想法，到前端面板的变化**：

```
① 模型决定更新任务
      │  调用工具：todo_write({ todos: [...] })
      ▼
② 工具 execute 执行（引擎调它）
      │  两个出口同时发生：
      ├──► 出口1（给模型）：返回 ToolResult
      │       "已更新：2 待办 / 1 进行中 / 0 完成"
      │       → 模型看到结果，决定下一步
      │
      └──► 出口2（给前端）：触发 onTodoWrite 回调
              │
              ▼
        ③ store.appendTodo(todos)   → 落盘成"会话事件"（第二节那种记录）
              │
              ▼
        ④ 推 SSE 帧 { type: "tool_todo", todos }
              │
              ▼
        ⑤ 前端 TaskPanel 组件收到 → 重新渲染面板
```

**注意②的两个出口**：一次工具调用，同时服务两个对象——
- **模型**拿到的是"结果文本"（它需要知道更新成功没有，决定下一步）
- **前端**拿到的是"新清单数据"（面板需要立刻刷新）

这就是"todo 状态更新和 toolCall 的关联"的答案：**todo_write 本身就是一个 toolCall（工具调用），状态更新是这次调用附带产生的两个副作用（回模型 + 推前端）**。

---

## 五、那"刷新页面后"呢？——权威值

上面⑤是"实时推送"（面板在对话过程中跟着变）。但如果**刷新浏览器**，所有推送都丢了，面板数据从哪来？

答案：**done 帧**——每次对话跑完，服务端把"最新任务清单"作为权威值一起发给前端：

```ts
// 服务端：从会话文件回溯，找最新的那条 todo 记录
send({ type: "done", todos: store.getLatestTodos() ?? [], ... });
```

`getLatestTodos` 的实现是"从会话树的叶子往回找，找到最近一条 todo 记录"——因为 todo 是会话事件，它天然**持久化在文件里**，刷新不丢。

> 这就是"会话事件"方案的第二个好处：**恢复**。如果 todo 是独立存储，恢复时要多读一个文件；作为会话事件，恢复 = 回溯会话，一条路径搞定。

---

## 六、前端：只读展示 + 一个聪明的关闭规则

**只读展示**：面板上的 todo 唯一写者是模型（通过 todo_write），用户不能直接改——就像"看板上的进度是团队系统自动刷的，不是谁手改的"。

**关闭规则**（抄 Reasonix 的交互）：任务没做完，面板**不许关**；全部完成了，才出现关闭按钮。而且关闭状态按会话隔离（localStorage 存 key 带 sessionId）——切换会话互不影响。

设计动机：任务没做完不该被藏起来；关闭是"清理已看完的清单"的单向动作。

---

## 七、踩过的坑：面板"卡在执行中"

有一次用户反馈：任务都结束了，面板还显示"执行中"，然后突然消失。

排查发现：**这一轮模型根本没调 todo_write**（它没更新任务清单），但面板还显示着上一轮 run 的残留状态。后来发送新消息时清掉了上一轮的残留。

这个坑背后是设计含义：**todo 的状态完全由模型的行为驱动**——模型不调 todo_write，面板就不会变。所以"面板显示什么" = "模型最后一次调 todo_write 时发了什么"。它不是服务端主动维护的进度条，是**模型行为的镜像**。

---

## 八、小结（30 秒版）

1. **存在哪**：todo 是会话事件（和消息混在同一文件、同生命周期），不是独立存储。
2. **怎么更新**：模型调 `todo_write`，**整表替换**（幂等，防模型漂移）；三态：pending / in_progress（最多一个）/ completed。
3. **和 toolCall 的关系**：todo_write 就是一次工具调用——**同一个调用两个出口**：ToolResult 回模型（它决定下一步），onTodoWrite 推前端（面板刷新）。
4. **刷新恢复**：done 帧带 `getLatestTodos()`（回溯会话找最新清单），持久化天然解决。
5. **前端**：只读展示 + 未完成强制可见、全完成才可关（按会话隔离）。
6. **坑**：面板是"模型行为的镜像"——模型不调工具，面板就不变。
