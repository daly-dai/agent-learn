# 偏函数封装：为什么"把参数提前绑进函数"能让核心架构不乱

> 最近在做 AI 编程助手（Agent）项目时遇到的一个架构问题，以及一个很通用的解法。
> 背景是 AI 项目，但问题本身在"框架 + 插件"这类架构里普遍存在。

---

## 一、先交代项目背景（写给没做过 Agent 的人）

AI 编程助手的运作方式大致是这样：用户提需求 → 程序把需求发给大模型 → 大模型说"我想调用某个工具"（比如读文件、改代码、执行命令）→ 程序执行工具、把结果回给大模型 → 大模型继续思考……如此循环，直到任务完成。

这个项目里有一个**核心循环**（代码里我们叫它"引擎"），它负责上面这个"思考 → 调工具 → 看结果 → 再思考"的循环。

**关键认知**：这个引擎应该是"通用机器"——不管工具是读文件还是执行命令，它只负责"调"，不关心每个工具具体干什么。

---

## 二、问题：我往引擎里塞了业务回调

有一次图省事，我把两个业务相关的回调直接塞进了引擎的配置里：

```ts
runEngine({
  ...
  onTodoWrite: (todos) => { /* 任务清单更新时通知前端 */ },   // 业务 A
  onAskUser: (question) => { /* 向用户提问时挂起等待 */ },    // 业务 B
});
```

两个回调都是**特定功能**的：一个属于"任务清单"，一个属于"向用户提问"。

一开始挺方便，但后来意识到不对：**引擎开始认识"任务清单"和"提问"这些具体业务了**。一旦我要换一个产品场景（比如不做编程助手、改成做数据分析助手），这两个回调就用不上了，引擎却还带着它们。

打个比方：发动机里装了导航仪。发动机本该是"把燃料变成动力的通用机器"，结果它开始管"你要去哪"——换一辆车，发动机就废了。

---

## 三、判断标准：引擎原则上不允许认识业务

我给自己定了一条规则：

> 引擎原则上不允许认识任何业务，除非业界成熟的做法也这样。

带着这条规则去翻了参考项目（一个成熟的开源 Agent 实现），结论是：**它的引擎也不认识业务**。它调工具时只传几个通用的运行时参数：

```ts
execute(toolCallId, params, signal, onUpdate)
// 没有业务！没有"任务清单"没有"提问"
```

而业务相关的东西（比如"这次对话的工作区""通知前端的方式"），是在**创建工具的时候用闭包提前绑进去的**。它的做法证明这条路走得通，我照着做了。

---

## 四、解法：偏函数——提前把参数"烙"进函数

核心一句话：

> 把"业务相关的东西"在【创建函数】的时候提前绑进去；函数【执行】的时候只接收"运行时才知道的东西"。

先看一个通用例子（不涉及我项目的术语）：

```ts
// 工厂函数：创建工具时，把回调提前绑进闭包
function createTool(onNotify) {
  return {
    name: "my_tool",
    // 执行函数只收运行时参数，回调已经在闭包里了
    async execute(args) {
      await onNotify(args.data);   // ← 用提前绑好的回调
      return { content: "完成" };
    },
  };
}

// 创建时绑（项目启动时做一次）
const tool = createTool((data) => console.log("通知外部:", data));

// 执行时只传运行时参数（每次调用时传）
await tool.execute({ data: "hello" });
```

**关键点**：`createTool(onNotify)` 返回的 `execute(args)` 就是一个**偏函数**——它已经"记住"了回调，调用时只需要最后一个参数。

我项目里的真实形态是这样（业务名保留，但你可以看到结构和上面完全一样）：

```ts
// 创建"更新任务清单"工具时，把"如何通知前端"这个业务绑进去
const todoTool = createTodoTool({
  onTodoWrite: (todos) => store.appendTodo(todos),  // 闭包捕获"这次"的 store
});

// 引擎执行时只传运行时参数
await todoTool.execute({ todos: [...] });
```

## 五、打个比方：半成品菜包

偏函数可以类比成超市的半成品菜包：

| 半成品菜包 | 偏函数 |
|---|---|
| 工厂里就把调料配好 | 创建时就把回调绑好 |
| 拿到手只需要下锅炒 | 调用时只需要传运行时参数 |
| 每包口味可以不同 | 每次创建绑的回调可以不同 |

"提前配好的部分"和"临时决定的部分"分开——这就是偏函数的本质。

---

## 六、这样设计有什么好处

**1. 核心循环保持干净**
引擎调工具只有一句话：`execute(args, signal, onUpdate)`。它不关心工具是任务清单还是提问——**换业务、加业务，引擎一行不用改**。内核稳定，整个项目才稳。

**2. 好测试**
测试工具时，回调可以注入假的：

```ts
const fakeNotify = vi.fn();
const tool = createTool(fakeNotify);
await tool.execute({ data: "hello" });
expect(fakeNotify).toHaveBeenCalled();
```

不需要真的连前端，测的是纯逻辑。

**3. 支持"每次运行一套配置"**
我的项目里，会话存储是每次请求新建的，所以工具必须在每次请求里重新创建，让闭包捕获"这一次"的存储。如果工具是全局单例，就拿不到"这一次"的存储了。偏函数 + 每次创建，正好解决。

---

## 七、这其实是一个通用模式

同样的套路，在很多地方有不同名字，本质是同一个东西：

| 常见叫法 | 大白话 |
|---|---|
| 依赖倒置 | 核心不依赖具体实现，具体实现反过来被"塞进"核心的接口 |
| 控制反转 | 不是核心调用业务，是核心留口子、业务来填 |
| 策略模式 | 同一个接口，换不同的策略 |
| 插件架构 | 核心稳定，插件各干各的 |

它们的共同点都是：**把可变的东西提前绑进一个稳定的接口**。

---

## 八、小结

1. 引擎（核心循环）应该保持通用，不该认识具体业务。
2. 判断标准：除非业界成熟做法也这样，否则不让业务进核心。
3. 解法：偏函数——创建时绑业务（闭包），执行时只收运行时参数。
4. 好处：核心干净、好测试、支持每次运行一套配置。
5. 本质：依赖倒置 / 控制反转 / 插件架构的通用手法。
