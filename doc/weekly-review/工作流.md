# 每周学习回顾与分享 · 工作流

> **触发**：schedule（每周五）
> **输入**：过去 7 天（上周末 + 本周一到周四，跨两个 `2026-Wxx` 文件夹）的素材池
> **核心原则**：能用自己的话讲出来、自圆其说，才是真的懂。分享不是输出环节，是认知检验机制。

---

## 一周循环

```
┌─────────────────────────────────────────────────────────┐
│  周一 → 周四：素材积累期（无压力，不整理）                  │
│  · 周一二三四：新功能开发、学习、开发计划拓展               │
│  · 周末：自由发挥（产出按日期归当周 Wxx，ISO 周）          │
│  · 所有产出自动进素材池：commits、笔记、走读、想法碎片       │
└─────────────────────────────────────────────────────────┘
                        ↓ 周五（环的闭合点）
┌─────────────────────────────────────────────────────────┐
│  周五：检验 + 输出日                                      │
│  ① 盘点素材 → ② 深化 1-3 个点 →                          │
│  ③ 【核心】讲出来（自圆其说，答不上=没懂）→                │
│  ④ 回炉补漏 → ⑤ 再讲直到通 → ⑥ 固化技术文档 → 发布论坛     │
└─────────────────────────────────────────────────────────┘
```

## 默认安排（可灵活调整，不写死）

| 时间 | 谁 | 干什么 |
|---|---|---|
| 周四晚 | **agent** | 盘点本周素材、整理碎片、扮演质询者检验理解 |
| 周五 | **同事/真人** | 讲出来、被反问、自圆其说（核心检验） |
| 周五后 | agent | 把"讲通的那一版"固化成本周技术文档 |

> 听众可选：真人（同事/技术群/论坛）为主，agent 质询兜底。每次自选。

## Phase 0 过程日志（贯穿整周，最该养成的一环）

**它存什么**：git 记不住的过程——思路、错误/卡点、决策（含为什么）、下一步。
**它不存什么**：代码/commit 内容（在 git）、完整对话（在 .traces/）、长文（在精读笔记）。

### 周归属与日期（2026-09-01 定，防"08-31 被记进 W35"类错误）

- **周文件夹 = ISO 周**：`2026-Wxx` 以**周一**为一周开始（W36 = 08-31 ~ 09-06），条目按 commit 发生日归属，**不按"周六起始"的循环划分**——循环是节奏，文件夹是坐标，两者不再混用。
- **日期先查后写，不凭印象**：写条目前先 `Get-Date` 确认"今天几号、周几"，再决定放哪个 `2026-Wxx`。LLM 凭感觉记日期不可靠（08-31 被误当周日记进 W35 的教训，与 08-27 误标 08-28 同类，commit 82a10ff 修过一次）。
- **周末产出**：周六周日的自由发挥产出按日期归当周文件夹，周五盘点时算入"过去 7 天"（上周末 + 本周一到周四）。

### 写入时机（三个，缺一不可）

| 时机 | 触发 | 写什么 |
|---|---|---|
| **commit 时**（主） | 每次 commit 前，随改动清单一起 | 该功能的完整过程总结，**带功能名 + commit hash**（如 `## 08-27 周四 · 功能：skills 筛选（commit: a1b2c3d）`） |
| **压缩前**（应急） | agent 察觉要压缩上下文时 | 本次会话至今的要点——压缩是唯一会丢的节点，必须丢之前落盘 |
| **周五盘点时**（兜底） | Phase 1 发现日志太薄 | 扫 `.traces/` 抢救补记（机器层永远在） |

**不是**：每轮对话都记——那会写出几十条废话。commit 时是主时机，因为它天然是功能单元边界，且和提交纪律（展示 → 确认）零负担衔接。

### 格式（每条三五句话，能看懂就行）

```markdown
## 08-27 周四 · 功能：skills 筛选（commit: a1b2c3d）
- 思路：41 个技能大多依赖 issue 工作流；我不用 issue，所以整条流水线都该砍
- 错误/卡点：以为 diagnosing-bugs 是收尾技能，其实是修 bug 全程
- 决策：移除 13 个到 skills-archive（为什么：无 issue 工作流 → tracker 流水线失效）
- 下一步：周五前把本周所学讲给同事听
```

### 为什么必须有它

会话压缩只影响 agent 的当前窗口，**不影响已落盘的文件**。
- `.traces/`（原始层）：✅ 压缩免疫，但机器格式不可读
- 过程日志（提炼层）：✅ 压缩免疫，人可读，周五盘点的素材
- agent 记忆：❌ 压缩即丢——过程日志就是把"丢之前"的那部分救下来

## Skill 触发映射（哪个步骤触发哪个 skill）

> 原则：**skill 是按需触发的工具，不是每个 Phase 的必选项**。哪个 Phase 需要哪种能力，才调对应 skill。

| Phase | 需要的能力 | 触发 skill | 说明 |
|---|---|---|---|
| Phase 1 盘点 | 汇总本周产出 | （无需 skill） | git log + 过程日志 + 笔记就是全部素材，不需要工具 |
| Phase 2 深化 | 查一手资料 | **`research`** | 对每个深挖点补官方文档/源码，追回一手源 |
| Phase 3 讲出来 | agent 兜底质询 | **`grilling`** | 无人可讲时，agent 用 grilling 的"设计树 + 轮次反问"模式扮演听不懂的听众 |
| Phase 4 回炉 | 补查漏洞 | **`research`** | 答不上的点再查一手资料 |
| Phase 5 再讲 | 同 Phase 3 | **`grilling`** | 同上 |
| Phase 6 固化 | 逐段塑形成文 | **`writing-shape`**（备选 `writing-fragments` 挖碎片） | ⚠️ 这两个是**用户触发**（disable-model-invocation），agent 不能自动调——需要用户说"开始成文"，或 agent 直接读 `C:\Users\25082\.agents\skills\writing-shape\SKILL.md` 按指令执行 |

**周一到周四（素材积累期）的技能**不归工作流管，是开发/学习时的日常工具：

| 场景 | 触发 skill |
|---|---|
| 写新功能 | **`tdd`** + **`vitest`** |
| 写完收尾 | **`code-review`**（双轴：Standards + Spec） |
| 改 bug | **`diagnosing-bugs`**（全程，不是收尾） |
| 验证想法 | **`prototype`** |
| 讨论定案 | **`to-prd`** |
| 接口设计 | **`codebase-design`** |

## Phase 明细

### Phase 1 盘点（周四晚，agent）
- 捞素材池：`git log --oneline` 本周 + **`00-过程日志.md`** + 笔记清单 + 走读/想法碎片（三源合并：git 给结果，日志给过程，笔记给沉淀）
- 产出：`01-周报.md`（本周做了啥、学了啥，清单体、真实、不怕丑）

### Phase 2 深化（周四晚 → 周五早）
- 挑 1-3 个最值得深挖的点
- 对每个点：`research` 补一手资料，直到能回答"为什么"

### Phase 3 讲出来（周五，核心）
- 找听众（真人或 agent 质询），用自己的话讲，不看笔记
- 听众反问，你答；**答不上 = 没懂 = 记下来**
- 讲的过程暴露的漏洞，进 `02-碎片.md`

### Phase 4 回炉（周五）
- 把答不上的地方回去搞懂（再看源码 / research / 问人）
- 只补漏洞，不重学全部

### Phase 5 再讲（周五）
- 直到自圆其说。讲不出来的地方就是没懂的地方。

### Phase 6 固化 + 发布（周五 → 周末）
- 把"讲通的那一版"整理成 `03-技术文档.md`
- 发布到技术论坛；反馈沉淀进 `04-反馈.md`，供下次改进

## 沉淀结构

```
doc/weekly-review/
  工作流.md                    ← 本文件（常驻参考，已被 AGENTS.md 第 11 条指针引用）
  2026-Wxx/
    00-过程日志.md             ← 过程层：思路/错误/决策（commit 时 + 压缩前写，贯穿整周）
    01-周报.md                 ← 盘点产物（写给未来的自己）
    02-碎片.md                 ← 整理期碎片 + leading word
    03-技术文档.md              ← 讲通后的固化（分享 + 发布用）
    04-反馈.md                 ← 发布后反馈、下次改进
```

- 周报/碎片：清单体，真实即可；技术文档：正式体，每段先锚定再依赖。
- 技术文档建议纳入 git；碎片/反馈可选。
- 判断"真懂"的唯一标准：**能讲出来、答得上反问**，而不是"写出来了"。
