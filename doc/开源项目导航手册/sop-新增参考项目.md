# 新增参考项目 SOP（架构解析 → 建立"功能→位置"索引）

> [返回索引](index.md)
>
> **为什么有这个机制（2026-08-31 用户定）**：新增参考项目不是"克隆完事"——**必须解析它的架构**，
> 把核心功能所在的路径记下来，下次想找某类知识时**直接进对应文件**，不用全局重头搜。
> 本 SOP = 确认存在（第 0 步）+ 架构解析（必做）+ 填导航卡（记录路径索引）。
> **克隆/更新代码由用户自己做**，AI 只负责"读懂 + 记下"。
> 上次加 langchainjs/opencode 是临时摸出来的、解析深度不齐——本机制把流程固定下来。
> **入口**：当用户说"我新增了一个参考项目 A"时，按本 SOP 执行（AGENTS.md 也有入口指引）。

## 流程总览

```
第 0 步 确认项目存在 → ① 架构解析 → ② 填导航卡 → ③ 回填 → ④ 验收
```

## 第 0 步 确认项目存在（先确认再动手）

用户说新增了项目 A 时：

1. **找项目**：先按名字在 `E:\agents-read\<A>\` 找（或用用户指定的路径）
2. **确认存在**：`Test-Path` 验证路径存在（zip 解压的可能是 `<A>-main\` 之类，以实际为准）
3. **不存在则先请用户放置**：克隆/解压是用户自己的事——找不到就说"没找到，请先放到 xxx"，**不要擅自克隆**

确认存在后才进入 ① 架构解析。

## ① 架构解析（核心！产出"功能→位置"索引）

用下面的清单过一遍，结果填进导航卡（模板见下）：

1. **识别技术栈 / 包管理**：顶层 `Get-ChildItem <项目> -Force` → TS（pnpm/turbo）/ Rust（cargo workspace）/ Go（internal/）/ Python（src/）
2. **组织哲学**：monorepo 分包（`packages/` / `crates/`）？一能力一包？一文件一能力？→ 决定"功能→位置"的推理方式
3. **定位核心引擎**：搜 `agent` / `loop` / `run` 文件名——**循环是每个 harness 的心脏，必须定位到**
4. **按 ETCLOVG 七层逐层定位**（理论坐标系 = `E:\agents-read\Agent-Harness-Survey-ZH-main` 的分类法，
   落地表见 `workspace/理论核心-ETCLOVG落地.md`）——**七层是穷尽的功能全景，逐层过一遍，没有的层也明说"该仓库无此项"**：

   | 层 | 我们关心什么 | 去参考项目找什么 |
   |---|---|---|
   | **E** 执行环境与沙箱 | 终端执行 / 沙箱隔离 | bash-executor / sandboxing / shell |
   | **T** 工具接口与协议 | 工具注册 / 参数协议 | tools / tool-call / tool-registry |
   | **C** 上下文与记忆 | 会话树 / 压缩 / 记忆 | session / compaction / memory |
   | **L** 生命周期与编排 | 循环 / 子 agent / todo / 计划 | agent-loop / subagent / todo / schedule |
   | **O** 可观测性 | 事件 / 轨迹 / 日志 | events / trace / rollout / telemetry |
   | **V** 验证与评估 | 测试 / 评测 | test-support / tests / eval |
   | **G** 治理与安全 | 审批 / 审计 / 只读分析 | permission / execpolicy / approval / shellsafe |
   | 附加 | UI / 模型适配（**非七层**，按项目实际补充） | frontend / ui / provider / llm |

   每项用仓库自己的词 grep（如 E 层：pi=`bash-executor` / codex=`sandboxing` / DSH=`shell`；
   找不到就明说"该仓库无此项"——**不是猜的**）
5. **找文档**：`docs/` 或 README 有没有中文/架构文档（DSH 就是"先读文档再读代码"）
6. **验证**：每个映射路径 `Test-Path` 存在；每个关键词 grep 有命中——**不是猜的**

## ⚠ 目录超级多怎么办（monorepo 几十个包：DSH 50+、codex 100+ crates）

这是最常见的坑，三个原则：

1. **只列"我们用到的"子集，不列完整树**——导航卡只收录 ETCLOVG 七层（E 执行/T 工具/C 上下文/L 生命周期/O 可观测/V 验证/G 治理）相关的包，其余目录提一句"还有 X 个包，按需进"即可
2. **包名/crate 名即功能名**——DSH 的 `packages/todo` = 任务面板、codex 的 `execpolicy` = 审批：想找什么功能直接进同名包，不用翻完整树
3. **先读文档再进代码**——`docs/` 或 README 是"地图的地图"（DSH 官方中文文档质量极高，先读它定位，再进对应包）；搜索时务必排除 `node_modules`（pi 的 node_modules 巨大）

## ② 填导航卡（模板见下）

按模板填：**定位 / 组织哲学 / 目录结构（只列核心，>30 项只列子集）/ 功能→位置映射（含"已读"列，如实标，没读就写"未读"）/ 搜索配方**。
新建文件 `<项目名>.md` 放到本文件夹（渐进式：一个项目一个文件），并在 `index.md` 的两个表（项目文件表 + 项目速览表）各加一行。

## ③ 回填

- `index.md` 项目文件表 + 项目速览表各加一行（上一步已做）
- **`PLAN.md` 的参考项目阅读地图不用改**（2026-08-31 定：**单一事实源**）——项目清单唯一在 `doc/开源项目导航手册/index.md`，
  那里只留一行引用，不各自维护（避免两套列表不同步）；新增项目只改 index 一处即可。

## ④ 验收清单（全部过才算完成）

- [ ] 每个映射路径 `Test-Path` 存在
- [ ] 每个搜索配方 grep 示例真实可命中
- [ ] 导航卡"已读"列如实标（没读就写"未读"）
- [ ] `index.md` 两个表都有新项目行
- [ ] **交叉验证（2026-08-31 加，教训：路径存在 ≠ 功能属实）**：派一个独立子代理抽查映射表中 3-5 条，**打开文件**确认内容与描述一致（目录名会骗人：guard/stats/guardian 看着像治理/观测，实际职责完全不同）——发现归类错误先改再算完成

> 如需把新 git 项目接入 C15 更新面板（页面点更新）：见 `../plan/c15-repo-updater.md`（registry 加行 + 测试同步 + 基线）——那是 C15 功能范畴，不是本 SOP 的必做项。
