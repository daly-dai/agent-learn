# 上下文压缩：对话太长时，让模型自己写"工作总结"

> 本文讲我们项目"上下文压缩"功能的完整故事：
> 为什么需要它 → 四个大项目分别怎么做 → 我们怎么取舍 → 具体怎么实现的。

---

## 一、为什么需要压缩（先讲问题）

模型的上下文窗口是**硬上限**：一次能"看到"的对话量是固定的（比如 DeepSeek 1M token，Anthropic 200K）。但对话是**无限增长**的——聊 100 轮、200 轮，迟早撞墙。

超窗了怎么办？三条路：

| 方案 | 做法 | 问题 |
|---|---|---|
| 硬截断 | 从最旧的开始丢 | 用户最初的意图、关键决定、文件路径全没了 |
| 不处理 | 直接报错 | 对话没法继续 |
| **压缩** | 把旧对话**重写成摘要**，摘要顶替旧消息 | 有损（细节丢失），但保住了"对继续干活有用的信息" |

**压缩的本质**：不是"删掉旧消息"，而是**让模型把旧对话读一遍，写一份"工作总结"**——Goal（用户要什么）、Progress（做到哪了）、Next Steps（接下来干嘛）。下一个模型看到总结就能接着干活，不用翻流水账。

还有两个隐藏理由：
- **省钱**：上下文越长，每次请求越贵（按 token 计费）。
- **注意力退化**：对话太长时，模型会"忘记"中间的内容（lost in the middle）——压缩顺便治这个。

---

## 二、两个 bug 逼我们认真做（症状驱动）

我们原本的"压缩"是**拼贴**：把旧消息原文用 `user: 内容` 的格式连起来当摘要。结果出了两个问题：

**Bug 1：页面渲染怪**。摘要伪装成 user 消息发给模型，前端分不清，把摘要当"用户说的话"渲染成大块文本。

**Bug 2：DeepSeek 400 报错**。压缩时切点（从哪里开始压缩）恰好落在"工具结果"上，它配对的"工具调用"被压进摘要了 → 模型看到一条孤零零的工具结果，前面没有对应的调用 → API 直接拒绝。

这两个 bug 说明：压缩这事儿不能糊弄，得认真设计。于是去读四个大项目的源码，看人家怎么做。

---

## 三、四家大项目怎么做（各学各的）

我们精读了 pi、codex、Reasonix、DSH 四个项目的压缩实现，一句话总结各家：

| 项目 | 核心做法 | 独门绝活 | 一句话人设 |
|---|---|---|---|
| **pi** | 独立请求调模型生成固定格式摘要 | **显式增量更新**（旧摘要作为参数带过去） | 最"教科书" |
| **codex** | 把会话交给 **OpenAI 服务端**压缩（本地压缩只是兜底） | 压缩后**保留用户消息原文**（用户的话不能改） | 最"工程" |
| **Reasonix** | **缓存对齐**（复用对话前缀让 KV 缓存命中，省钱） | **经济性检查**（省不下 400 token 就不压） | 最"省钱" |
| **DSH** | 缓存对齐 + **检查点格式**（8 段结构化摘要） | 摘要格式就是"给下一个模型的交接单" | 最"产品化" |

**四家的共识**：压缩 = 调模型把旧对话重写成"交接单"；摘要伪装成 user 消息回上下文；工具结果不能成为切点。

**四家的分歧**（也是我们要做选择的）：
1. 摘要请求怎么调？独立请求（pi）还是复用对话前缀省钱（Reasonix/DSH）？
2. 摘要什么格式？固定结构（pi/DSH）还是自由发挥（codex）？
3. 多次压缩怎么不丢信息？显式参数（pi）还是提示词里"软要求"（Reasonix/DSH）？

## 四、我们的 10 个取舍（每个都有理由）

先看约束：我们是**教学项目**（可读性 > 性能）、只用 **DeepSeek**（没有 codex 那种服务端压缩端点）、**没 key 也能跑**（MOCK 模式）。这三个约束决定了取舍。

| # | 决策 | 选谁 | 一句话理由 |
|---|---|---|---|
| D1 | 摘要请求：**独立请求** | pi | 缓存对齐省的是 KV 缓存钱，但实现复杂、DeepSeek 计费不透明——"复杂度换钱"现在不划算 |
| D2 | 摘要格式：**pi 结构 + DSH 两段** | pi+DSH | pi 的 Goal/Progress/Next Steps 保证结构稳定；加上 DSH 的 Files/Errors 两段（我们天天碰文件，有用） |
| D3 | 增量更新：**显式机制** | pi | pi 把旧摘要当参数 + 专用提示词，最可靠；Reasonix/DSH 只是提示词"软要求"，模型可能不听话 |
| D4 | **不引入** retainedTail | 我们现状 | pi 物理删消息所以要存保留区；我们只追加不删，一个指针就够（详见第七节） |
| D5 | 切点：按条数 + toolResult 前移 | 我们现状 | 教学版简单规则，先跑通 |
| D6 | **经济性检查** | Reasonix | 一行判断：待压区域太小就不压——省 200 token 却花一次 API 调用，不划算 |
| D7 | **工具参数防泄漏** | Reasonix | 序列化时参数只写 key 名，防止长 JSON 撑爆摘要、防敏感信息泄漏 |
| D8 | 失败**降级拼贴** | 我们现状 | 压缩是"保险"，失败不能拖垮对话——降级到拼贴保信息 |
| D9 | **截断检测** | DSH | 模型吐了空串/半截 → 返回失败，不落半截摘要（fail-closed） |
| D10 | 文件列表附摘要 | pi | 扫描被压消息里碰过的文件，附在摘要末尾 |

**一句话总结取舍逻辑**：**拿 pi 的工程严谨打底（格式/增量/分离），吸收 Reasonix 的成本意识（经济性/防泄漏），参考 DSH 的领域格式（Files/Errors），拒绝 codex 的服务端依赖和缓存对齐**。

## 五、怎么实现的：三步走

实现分三个文件，职责各一：

```
① 准备（纯计算，不碰模型）          lib/session/store.ts 的 prepareCompaction
   回答：压哪些？留哪些？上次摘要是什么？
      ↓
② 生成（调模型）                    lib/summarize.ts 的 generateSummary
   回答：把要压的消息变成提示词，让模型写总结
      ↓
③ 落盘（存起来）                    lib/session/store.ts 的 commitCompaction
   回答：把摘要存进会话文件，下次对话用它顶替旧消息
```

**为什么拆成三步？** ①③ 是纯逻辑（不碰模型），**可以单独写测试**；② 是唯一碰模型的地方，放产品层（route.ts）组合。这和 pi 的 `prepareCompaction → compact → 落盘` 完全对齐。

### 第 ① 步：准备（纯计算）

```ts
prepareCompaction(maxTokens, keepRecent) {
  // 1. 算当前上下文多大，没超阈值 → 不压
  if (tokensBefore <= maxTokens) return undefined;

  // 2. 找上一次压缩的摘要（增量更新用，第三节 D3）
  prevCompaction = 路径上最后一个 compaction 记录;

  // 3. 选切点：保留最近 N 条，第一条不能是"工具结果"（孤儿 tool 防护）
  keepFrom = 末尾往前数 N 条;
  while (切点落在 toolResult 上) keepFrom -= 1;   // 往前挪，宁可多留

  // 4. 返回"要压什么"给产品层
  return { messagesToSummarize, previousSummary, firstKeptEntryId, tokensToSummarize };
}
```

### 第 ② 步：生成（调模型）

两个关键函数：

**序列化**：把消息变成模型好读的纯文本

```
[User]: 帮我写排序
[Assistant]: 好的，我来写…
[Assistant tool calls]: write_file({path, content} (2 keys))   ← 参数只写 key 名（D7）
[Tool result]: 已写入 sort.ts                                    ← 超过 2000 字符截断
```

**调模型**：

```ts
const result = await model.complete({
  systemPrompt: "你是摘要助手，只输出结构化摘要",
  messages: [user 消息 = <conversation>对话文本</conversation> + 摘要指令],
  tools: [],                    // ← 不带工具：不是让模型干活，是让它写总结
});
if (result.stopReason === "error") return null;   // 失败 → 降级信号
if (摘要为空) return null;                         // 半截 → 不落盘（D9）
return 摘要文本;
```

### 第 ③ 步：落盘 + 接线

```ts
// route.ts（每次对话跑完后）
const prep = store.prepareCompaction(阈值, 保留条数);
if (prep && prep.tokensToSummarize >= 400) {        // 经济性检查（D6）
  const summary = MOCK 模式
    ? 拼贴降级                                        // 没 key，不调模型（D8）
    : (await generateSummary(model, prep.messagesToSummarize, {
        previousSummary: prep.previousSummary,        // 增量：信息链不断（D3）
      })) ?? 拼贴降级;                                 // 失败兜底
  await store.commitCompaction(prep, summary);
}
```

## 六、增量更新：为什么"多次压缩"不丢信息

对话太长会压缩**好几次**。问题来了：第二次压缩时，模型只看到"上一次摘要之后的新消息"——它不知道上次摘要写了什么，怎么办？

**答案是增量更新**：把上一次的摘要作为输入一起带给模型，让它"保留旧的 + 合并新的"。

```
第二次压缩时模型看到的输入：
<conversation>
[User]: 把排序改成降序          ← 新消息
</conversation>

<previous-summary>                ← 上一次的摘要（从会话文件里捞出来的）
## Goal
用户要一个排序算法（要求降序）
</previous-summary>

The messages above are NEW messages to incorporate into the existing
summary provided in <previous-summary> tags.
RULES: PRESERVE all existing information... ADD new progress...   ← UPDATE 提示词
```

结果：第二次的摘要 = 第一次摘要的信息 + 新进展。**每次压缩都站在上一次的肩膀上，信息只会累积**——就像写周报时附上上周的周报，目标从第一周带到最后。

> 类比：没有增量 = 每次写周报只看本周记录 → 上周定的目标全没了；有增量 = 每次附上上周周报 → 越写越完整。

## 七、存储模型决定设计：我们为什么"不抄" pi 的 retainedTail

这是最有意思的一个决策——**同一个问题，两个项目答案不同，因为底层存储不一样**：

| | pi | 我们 |
|---|---|---|
| 被压的旧消息 | **物理删除**（从会话里真删了） | **只追加不删**（JSONL 文件一行行追加，从不删） |
| 那"保留区"怎么找回？ | 必须把保留的消息**存进压缩记录**（retainedTail），否则删了就没了 | 不需要——消息还在文件里，用 `firstKeptEntryId`（一个指针）就能定位 |
| 代价 | 文件不膨胀 | 文件一直长大（教学项目无所谓） |
| 好处 | — | 原始数据永远在，可回放、可审计 |

**结论**：pi 需要 retainedTail 是因为它"删"，我们不删所以不需要。**抄别人的设计要抄思想，不是抄表面**——先看人家的存储模型和你一不一样。

延伸回答一个常见疑问：**压缩后旧消息还在吗？**
- **在**。JSONL 只追加不删，被压的消息永远在文件里（像账本）。
- 只是 `buildContext`（给模型拼上下文的地方）会**过滤**——只输出"摘要 + 最近保留的 + 新消息"，旧消息"眼不见"但"存在"。

另一个疑问：**摘要只有一个吗？**
- 文件里**有很多条**（每次压缩追加一条 compaction 记录）。
- 但给模型看的上下文里**永远只有最新一条**——旧摘要被"摘要的摘要"合并掉了（增量更新）。

## 八、小结（30 秒版）

1. **为什么**：上下文窗口有限、对话无限 → 压缩 = 让模型写"工作总结"顶替旧消息。
2. **四家对照**：pi 教科书（显式增量）、codex 服务端（用户原话保留）、Reasonix 省钱（缓存对齐+经济性）、DSH 产品化（检查点格式）。
3. **我们的取舍**：拿 pi 打底（格式/增量/分离）+ Reasonix 成本意识（经济性/防泄漏）+ DSH 领域格式（Files/Errors），拒绝 codex 服务端和缓存对齐。
4. **实现**：三步走——准备（纯计算可测）→ 生成（调模型）→ 落盘。
5. **关键概念**：增量更新（信息链不断）、存储模型决定设计（不抄 retainedTail）、经济性检查、fail-closed、MOCK 降级。
