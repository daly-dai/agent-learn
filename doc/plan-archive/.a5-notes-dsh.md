## DSH 架构：三层 seam（最重要的设计）

```
packages/web/
├── web/                      ← ① web 能力 seam（ctx.web）：provider 注册/选择/配额
├── web-search-deepseek/      ← ② 搜索 provider（插件）：DeepSeek 原生 web search
├── web-search-exa/           ← ② 搜索 provider（插件）：Exa
├── web-search-perplexity/    ← ② 搜索 provider（插件）：Perplexity
├── web-fetch-http/           ← ② 抓取 provider（插件）：HTTP(S)
└── tool-web/                 ← ③ 模型面工具（web_search / web_fetch）
```

**关键原则（index.ts:2-5）**：tool-web 拥有 schema、校验、提示词、限额、展示——**永远不碰具体 provider**；provider 是独立插件，可插拔可替换。启用控制注册；provider 不可用时工具仍可见，执行时才结构化报错。

## 决策点 1：搜索后端选型（决定抄谁）

DSH 的 DeepSeek provider（web-search-deepseek）：
- **端点**：`https://api.deepseek.com/anthropic/v1/messages`（Anthropic 兼容 Messages API，**不是**我们用的 chat/completions）
- **机制**：发一次完整 Messages 模型调用，带原生 `web_search_20250305` 服务端工具
- **返回**：结构化 `web_search_tool_result` 块（url/title/page_age + citations）
- **成本**：每次搜索 = 一次完整模型轮次（延迟 + 生成 token），比纯检索端点重
- **key**：复用 `DEEPSEEK_API_KEY`——**我们现有 key 就能用，零新增配置**
- **严格模式**：无 tool_result 块就抛错，绝不从模型文本抓 URL（README:13）

vs Exa / Perplexity：专用检索端点，更轻，但要额外 API key + 付费。

**我们的现状**：已有 `DEEPSEEK_API_KEY`（.env.local），且 config.ts 的 provider 就是 deepseek——**走 DSH 的 DeepSeek provider 路线是零新增成本**。但需验证 `api.deepseek.com/anthropic/v1` 对我们 key 是否可用（可能 DeepSeek 已下线 Anthropic 兼容端点？需实测）。

## 决策点 2：web_fetch 的 HTML→文本转换（DSH 做法）

`tool-web/src/fetch.ts`：
- **turndown**（HTML→Markdown）+ `@joplin/turndown-plugin-gfm`（GFM 表格/删除线）
- `remove(['script','style','noscript'])` 丢非内容元素
- **防攻击深度上限** `MAX_CONVERSION_DEPTH = 512`（fetch.ts:102）：HTML 嵌套超深直接原样透传（domino 树遍历是超线性的，恶意页面能卡死同步转换）
- 输出上限 `DEFAULT_FETCH_MAX_OUTPUT_CHARS = 200_000`（index.ts:34）
- 超限截断 + footer `(Content truncated. Fetch a more specific URL or section for the full text.)`
- 头部 `Fetched <url> (HTTP <status>)`
- **memo 缓存**：render 和 presentationMeta 两次调用共用一次转换（WeakMap 按 result 缓存）

## 决策点 3：web_search 参数与输出（DSH 做法）

- 参数：`queries: string[]`（**数组，不是单字符串**！）1-4 个（WEB_SEARCH_MAX_QUERIES=4）
- 多查询并发执行 + 按 URL 去重 + round-robin 合并 + 上限 8 个源（WEB_SEARCH_MAX_RESULTS=8）
- 输出：`{ content?, sources: [{url,title?,snippet?,publishedAt?}], truncated }`
- 模型看到的文本：provider 答案（如有）+ `Sources:\n- [标题](url) — snippet (date)` + 截断提示 + **"Cite the relevant URLs above as markdown links in your answer."**
- 系统提示词也带工具用法说明（search.ts:316-322）
- 超时：30s 默认（tool 级 timeoutMs，部署策略不是模型参数）

## 决策点 4：错误处理（DSH 做法）

- `WEB_PROVIDER_ERROR`（provider 失败）/ `WEB_ABORTED`（取消）
- HTTP 重定向在接触 Location 前拒绝（安全）
- 凭据缺失 → `WEB_PROVIDER_CREDENTIAL_MISSING`
- 无结果 → `No results found.`

## 值得抄的点（暂列）

1. **工具/provider 分层**（seam）：工具不碰 provider——我们将来加 Exa 只需新 provider 插件
2. **queries 数组**：一次搜多个查询，比单 query 省轮次
3. **fetch 防深度攻击**：MAX_CONVERSION_DEPTH 这个细节很工程
4. **turndown + GFM**：HTML→Markdown 比纯文本提取保留结构
5. **"cite the URLs"提示**：引导模型带来源，防幻觉

## 补充：smolagents（Python 轻量框架）——最简实现的取舍

> 精读走读 19（子代理产出，源码 `smolagents-main/src/smolagents/default_tools.py`）

- **工具形态**：`web_search` = 4 个类共用 name（DuckDuckGoSearchTool:104 免费 / GoogleSearchTool:162 / ApiWebSearchTool:249 默认 Brave / WebSearchTool:342）；`visit_webpage` 独立（VisitWebpageTool:491）。Tool 基类强制 name/description/inputs/output_type 四件套
- **后端**：DDG 用 `ddgs` 包（免费无 key，`ddgs.text(query, max_results=10)` 一行）；Api 版默认 Brave（BRAVE_API_KEY），可换 SerpAPI/Serper/Exa
- **限流**：手写最小间隔 sleep（`1/rate_limit`），10 行搞定
- **抓取**：requests GET(20s) → markdownify 整页 HTML→Markdown → 压空行 → 截断 40000 字符。**无正文提取、不下载图片**——噪音交给 LLM 过滤（复杂度从工具移到模型）
- **输出**：直接给 LLM 的 Markdown 字符串（`[title](url)\nbody`），不搞结构化 schema
- **反面教训**：错误处理不一致——DDG/Google 无结果抛异常，Api/Brave 和 Visit 返回错误字符串，限流代码复制两份。我们实现应统一"异常冒泡给 agent 循环"一种策略
- **设计亮点**：免费后端做默认 + 同 name 换付费后端，agent 无感切换

### smolagents vs DSH 的第一眼对比

| 维度 | DSH | smolagents |
|---|---|---|
| 搜索后端 | provider 插件（DeepSeek 原生 / Exa / Perplexity） | DDG 免费默认，可换付费 API |
| 工具面 | 结构化 schema + 展示卡（meta 持久化） | 纯 Markdown 字符串，不搞 schema |
| 抓取 | turndown + GFM（保留结构）+ 防深度攻击 | markdownify 整页 + 截断，无防护 |
| 错误 | 结构化 WebError 族 | 不一致（抛异常/返回字符串混用） |
| 分层 | tool 与 provider 严格分离（seam） | 类内 self-contained，无 provider 抽象 |

## 补充：CodeWhale（Rust）——"完全体"参考（安全深度最高）

> 精读走读 20（子代理产出，源码 `CodeWhale-main/crates/tui/src/tools/web/` 9 文件 + 3 工具面）

- **工具形态**：web_search / fetch_url / Web（action=search|fetch|wait）三工具**共享同一套安全/解析/缓存/引用基础设施**（mod.rs:1-4）
- **后端链**：11 种后端（ProviderNative + Bing/DDG/Firecrawl/Tavily/Bocha/Metaso/Searxng/Baidu/Volcengine/Sofya），默认 keyless Firecrawl；`SearchBackendChain` 三级降级（provider-native→API→DDG 兜底）每条 hop 留痕
- **安全（最厚模块 guard.rs）**：仅 http/https；`is_restricted_ip` 覆盖私网/云元数据 169.254.169.254 等；**DNS 预解析 + pin**（校验过的 IP 绑进 reqwest .resolve()，防 TOCTOU）；**禁环境代理**防绕过；重定向逐跳校验；响应头滤 set-cookie/api-key
- **引用注册表**：ref_id = sha256(namespace\0url) 前 16 位，URL 凭证剥离，跨会话失效，防引用伪造
- **溢出=可恢复**：全文落盘 + `retrieve_tool_result` 恢复，不是截断丢信息
- **诚实性**：receipt 把"requested vs honored/degraded"全量披露给模型（连 recency 被忽略都告知）
- **测试即文档**：SSRF 全向量 + CVE 回归（GHSA-88gh-2526-gfrr）

### 教学取舍（初步）

CodeWhale 是"完全体"：全抄会淹没教学点。值得吸收：① 诚实性（披露 degraded）② URL 凭证剥离 ③ fail-closed 错误不降级；暂缓：DNS pin / 引用注册表 / 后端链（等真需要时）。

## 补充：codex（OpenAI）——瘦客户端胖服务端 + 单工具多命令

> 子代理产出（源码 `codex-rs/ext/web-search/` + `codex-api/src/{search,endpoint/search}.rs`）

- **工具形态**：命名空间工具 **`web.run`**（不是 web_search/web_fetch 两个）——10 个命令字段：search_query / image_query / open / click / find / screenshot / finance / weather / sports / time + response_length。搜索、抓取、点链接、页内查找、截图、垂直数据全收敛成一个工具，模型可一次调用并行多命令
- **后端**：**OpenAI 自有搜索 API**（POST 到 provider base_url + `alpha/search`），复用现有登录认证，**无独立搜索 key**；客户端无任何搜索库依赖
- **瘦客户端**：本地只做协议 + 上下文裁剪 + 透传；去重/正文提取/HTML 清洗/引用合规**全在服务端**
- **上下文精打细算**：搜索请求只带最近 2 条用户消息 + ≤1k token assistant 文本（history.rs:24-25）
- **双轨切换**：standalone（web.run 扩展）与 hosted（Responses API 原生 web_search 工具）二选一，core 按 provider 能力 + feature flag 裁决
- **错误两级**：参数解析失败 → `RespondToModel`（回模型改参数重试）；provider/搜索失败 → `Fatal`（终止本轮）
- **安全**：无客户端 SSRF 防护（抓取在服务端，责任在服务端）；`allowed_callers=[Direct]`（只有模型能调，shell 不能）；域名 allowlist；`web_search_mode` 四档 disabled/cached/indexed/live 映射服务端 external_web_access
- **无独立 web_fetch**：抓取是 web.run 的 open/click/find/screenshot 命令

### codex 的取舍对我们最有冲击的一点

"**单工具多命令**"——一个 web.run 收敛搜索+抓取+点链接+截图。但它的前提是"胖服务端"（OpenAI 服务端替它做了一切）。我们是自研，抓取清洗得自己做——所以不能照抄"单工具"，但"**减少工具数量**"的思考方向值得保留（我们做 2 个工具 web_search/web_fetch 是合理折中，不学它收敛成一个）。

## 补充：Reasonix（Go）——服务端搜索 + 自研抓取（两条腿走路）

> 精读走读 22（亲自读，源码 `internal/agent/server_search.go` + `internal/provider/server_search.go` + `internal/tool/builtin/webfetch.go` + `internal/config/web_search.go`）

- **web_search = 纯服务端**：Anthropic 兼容 Messages API 的 `web_search_20250305` 工具，Reasonix 只做转发/格式化/事件化（ReadOnly: true）；结果模型就 `{Title, URL}` 两字段
- **关键验证**（config/web_search.go）：`SupportsServerWebSearch` 只认 kind="anthropic"/"responses"，**明确排除 OpenAI Chat Completions**（"DeepSeek's documented chat-completions tool contract only supports functions"）——**我们现在的 chat/completions 端点没有服务端搜索**；`IsOfficialDeepSeekWebSearchEndpoint` 确认 `api.deepseek.com/anthropic` = 官方搜索端点；`EffectiveWebSearch` 对官方端点**默认开启**
- **web_fetch = 自研 585 行**：SSRF 防护（**DNS 预解析 + 校验后直连**防 rebinding；blockedFetchIP 含 CGNAT 100.64/10 防阿里云元数据；loopback 允许因为 agent 已能 bash 到 localhost）+ 15s/1MiB + 手写 HTML tokenizer（不用 readability）+ 输出头 `status · type · bytes`

### Reasonix 对我们最重要的两条

1. **搜索与抓取分离哲学**：搜索用服务端（零代码、免 key 清洗），抓取自研（可控可教学）
2. **证实 DSH 路线可行**：官方 DeepSeek Anthropic 端点 + web_search_20250305 + 现有 key = 官方支持（Reasonix 和 DSH 两家互相印证）；且明确告诉我们"chat/completions 上没有服务端搜索"
