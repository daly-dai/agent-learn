# 归档：二、四个直接问题的回答（Phase 0 时期）

> 来源：PLAN.md 第二章（2026-08-26 PLAN 拆解时归档）。起步时的架构答疑，结论已定案并执行，保留作历史参考。

### Q1：单轮对话逻辑是否已经算"初步框架"？
**是。** 而且不止"初步"——协议、引擎、工具、SSE、前端五层都已打通，是一个可以真实运行的闭环。

### Q2：需要下载 sse.js 或 openai SDK 吗？
**都不需要。**

- **sse.js**：不需要。项目已手写 SSE——服务端 `ReadableStream` + `text/event-stream`，客户端 `fetch` + `res.body.getReader()`。浏览器原生 `EventSource` 不支持 POST body，而现在的 `fetch` 方式已绕开这个限制。
- **openai SDK**：不必须。DeepSeek 提供 **OpenAI 兼容** 接口，直接用 `fetch` 调 `https://api.deepseek.com/chat/completions` 即可。用 `fetch` 手写 adapter 更符合"做中学"——能看清"provider 字段 → 统一协议"这一层转换（pi 的 `pi-ai` 层做的事）。以后要接多家供应商、要 OAuth/缓存等高级能力时，再引入 SDK 或自己抽 `pi-ai` 那样的适配层。

### Q3：Next.js 能支撑这些功能吗？
**能，全部能。** 本地跑（localhost）几乎没有限制：

| 功能 | Next.js 方案 | 备注 |
| --- | --- | --- |
| 单/多会话、记忆 | Route Handler + 磁盘 JSONL / SQLite | 与 pi 的 JSONL 会话树一致 |
| 文件增删改查 | Node runtime 下 `node:fs` | 需 `export const runtime = "nodejs"` |
| 终端运行 | Node runtime 下 `node:child_process` + SSE 推流 | 需进程管理 + 安全白名单 |
| task 面板 | 前端组件 + 会话内持久化 | 与消息一起存进 session |
| 对话面板 | React + SSE（已通） | 继续加会话列表/分支树 |

**唯一的边界提醒**：交互式 TTY（如 `vim`、需要回显的 REPL）比"执行命令并流式返回输出"难得多。前期只做"跑一条命令 → 流式吐 stdout/stderr → 支持 Ctrl-C 终止"就够用，不要一开始做完整 pty。

### Q4：现在就该换架构吗？
**不换。** 换架构（比如迁到 pi 的 Bun monorepo、或换成 Python + FastAPI）是"过早优化"：

- 现有抽象（`TeachingModel` / `ToolRegistry` / `runAgentLoop` / `types.ts`）**已经是 pi 三层思想的雏形**，换架构只会丢掉能跑的代码。
- Next.js 能一路支撑到全部功能。真正需要"换/拆架构"的信号是：需要常驻后台的 agent 服务独立于 web 服务、要发 CLI 工具、要跨进程复用内核。到那时把 `lib/` 抽成共享包（monorepo）即可——这也是 pi 的分层给出的答案。

> 现状（2026-08-26）：结论全部兑现——未换架构，未引 SDK，SSE 手写，TTY 留作 C 阶段终端加固。
